# Memory

Этот документ описывает реализованные контуры долговременной памяти и их
границы. Это описание текущей системы, не целевая схема.

## Области памяти

В системе есть три независимых вида контекста:

| Контур | Для чего нужен | Хранение и жизненный цикл |
|---|---|---|
| Контекст чата | Ссылки на проекты, файлы, намерения и незавершённую работу внутри одного чата | Типизированный revisioned snapshot; правила в [Chat Context Memory](CHAT_CONTEXT_MEMORY.md) |
| Диалоговые факты | Устойчивые личные и tenant-сведения, подтверждённые по сообщениям и результатам инструментов | `facts` и `FactObservation`; запись асинхронно после синтеза ответа |
| Semantic Memory | Знания о компании и проектах, извлечённые из документов с provenance | `MemoryItem`, `MemoryClaim`, источники, evidence и relations; публикация через документный review pipeline |

Runtime trace хранится отдельно в `runtime_execution_events`. Он не является
источником памяти. Текущее состояние внешней системы всегда получают через
tool, а основания из документов проверяются через RAG.

## Диалоговые факты

После ответа chat-worker запускает `FactExtractor`, `FactCompactor` и
`FactReconciler`. Кандидаты без evidence не публикуются. Подтверждённые
пользовательские и tenant facts попадают в ограниченный runtime snapshot;
Sandbox overlays остаются локальными запуску. Project facts из диалога не
публикуются: проектная Semantic Memory должна происходить из source-backed
документов.

Стартовый профиль ранжируется по запросу и сохраняет место для обоих владельцев.
Факты вне этого среза доступны через `memory.search` с `scopes: ["user", "tenant"]`
и необязательным точным `fact_subject`. Поиск читает только подтверждённые,
не заменённые записи текущего пользователя и tenant. Результат содержит ID,
владельца и источник каждого факта. Разные значения одного subject возвращаются
с `fact_conflict` и требованием уточнения; документный RAG такой конфликт не разрешает.

Диалоговый writeback создаёт только user/tenant facts. Сообщение в чате не
публикует термин и не меняет определение в корпоративном глоссарии.

## Документный глоссарий

Подробный контракт описан в [Корпоративном глоссарии](../GLOSSARY.md).

`GlossaryTerm` — единая утверждённая терминология: каноническое название,
aliases и общая расшифровка. У термина нет team/project-применимости или локальности.
Термины извлекаются из документов любого access scope и поступают в общую
очередь проверки. Публикация требует решения администратора; автоматическое
утверждение запрещено. Карточка термина отделена от карточки атома памяти.

Значения и определения, зависящие от контекста, правила и параметры хранятся
отдельными атомами памяти с team/project-скоупами и ссылками на термин.
Общая расшифровка не заменяется проектным значением. Изменение общей расшифровки
требует явного подтверждения с причиной.

Runtime и все представления читают один каталог активных утверждённых терминов.
Происхождение не определяет доступность термина: архивирование или новая версия
документа не отменяет утверждение. При удалении исходного кандидата nullable-ссылка
обнуляется, термин остаётся. Миграция `0181` устанавливает этот контракт и новый
промпт извлечения терминов без ограничения по access scope.

## Semantic Memory из документов

1. Для документа действует политика коллекции либо явная настройка документа.
   Применимость выбирается отдельно для каждого извлечённого утверждения.
2. Активный ingest dispatch запускает shadow extraction. Результаты сохраняются
   как snapshot и кандидаты с ссылками на исходные sections, затем проходят
   conflict check и попадают в административную очередь.
3. Администратор утверждает или отклоняет кандидата. Утверждение термина
   публикует определение с документным источником; утверждение знания публикует
   `MemoryItem`/`MemoryClaim` с источником, применимостью и видимостью.
   Для публикации знания нужна подтверждённая применимость по team/project
   либо явное подтверждение внепроектного знания без адресата. Связь с термином
   применимость не задаёт. Некорректное содержание и конфликты блокируют публикацию.
4. Документ можно повторно исследовать; состояние и trace задачи доступны в
   админке. Изменения источника могут сделать прежнее знание устаревшим.

Знания имеют типы `description`, `relationship`, `rule`, `constraint`,
`procedure` и `decision`; glossary terms обрабатываются отдельно. Процедуры и
нормативные типы проходят typed content validation. Состояния semantic item:
`active`, `uncertain` и `stale`.

Изучение и публикация идут только через staging/review pipeline.
После commit ручного утверждения отправляется задача обновления векторного индекса.
Сбой доставки не отменяет опубликованную запись; периодическая reconciliation
повторяет индексацию и удаляет недействительные записи из производного индекса.

## Чтение в runtime

`memory.search` — единственная публичная system operation для bounded search
долговременной semantic memory, опубликованных терминов и user/tenant facts.
Она проверяет доступ к источнику и применимость и возвращает ограниченные результаты с
provenance. Она не предоставляет доступ к таблицам и не отвечает за текущее
состояние внешних систем.

Перед лимитами лексического и векторного поиска PostgreSQL отбирает действующие
опубликованные claims с доступным источником и подходящими областями, типами и
категориями. Qdrant получает допустимые ID. Совпадение термина или его alias
также находит утверждения, связанные с этим термином через утверждённый candidate,
даже если написание термина отсутствует в тексте правила.

Перед маршрутизацией TurnPreflight получает только механические подсказки
опубликованного глоссария и каталога проектов. При `recall` runtime выполняет ограниченный
поиск с определениями и ссылками на секции документов, затем повторно вызывает
TurnPreflight; при выполнении planner и агенты могут
вызывать `memory.search` по мере необходимости. Ни один путь не подмешивает
полный дамп памяти.

## Интерфейсы

- Пользовательские «Глоссарий», «Память проектов» и «Глобальная память» —
  read-only виртуальные коллекции, не строки `collections`.
- При загрузке документа можно выбрать политику Semantic Memory. Применимость
  настраивается тегами в review каждого знания; доступ определяется источником.
- Админка показывает глоссарий, опубликованные знания, очередь document
  candidates, конфликты и trace extraction. Изменение semantic content
  проходит через решение по кандидату и источник, а не произвольное
  редактирование опубликованной записи.
- Кандидат и опубликованное знание открываются одним компонентом карточки
  через отдельные маршруты. Общие вкладки: обзор, содержимое, связи и применимость,
  происхождение. Вкладка «Связи и применимость» разделяет условия применимости
  и один блок связей с полями проектов, команд и терминов. Кандидат открыт
  для редактирования; утверждение сохраняет поля и публикует знание одной
  транзакцией, оставляя карточку открытой с новым статусом. В опубликованной
  карточке кнопка в заголовке страницы включает редактирование связей; доступны
  сохранение и отмена. Сохранение обновляет скоупы всех source claims и связи
  их утверждённых кандидатов, проверяет коллизии идентичности атома и запускает
  переиндексацию. Содержание, условия, доказательства и доступ источника
  сохраняются. Источники и полные фрагменты документа находятся в происхождении.
- Промпт роли `document_memory_extractor` и настройки этапов доступны в
  Platform Admin.

## Доступ и доказательства

Публикуемое знание связано с документом и section evidence. Tenant visibility
проверяется для content, aliases, relations и evidence. Общий project catalog
не ограничивается tenant; лексические aliases общие. Сейчас видимость
semantic content определяется доступом к source claims. Память является подсказкой с provenance, а не доказательством
текущего состояния системы или разрешением на операцию.

Общая политика чтения используется runtime, административными проекциями и
индексацией: активный claim должен ссылаться на resolved candidate текущей
попытки последнего snapshot документа с совпадающей версией источника. Архивные
документы, неутверждённые и устаревшие claims исключаются.
Для collection-источников проверяется фактическое членство документа в разрешённой
коллекции по runtime RBAC, включая default policy и приоритет пользовательского
запрета. Tenant сам по себе не разрешает чтение collection-документа; доступная
общая коллекция может содержать источник другого tenant. Эти проверки действуют
до выбора текста, связей и evidence.

## Две ветки применимости: команды и проекты

`memory_scopes` содержит только `team` (кому адресовано знание) и `project`
(где оно действует). ID и ключ стабильны, название и aliases редактируются.
`project_type` — тип конкретного проекта: например IAAS, SAAS, колокейшен;
он не создаёт третью ветку фильтрации. `product` не является типом скоупа.

Каждый атом независимо выбирает значения обеих веток: конкретные ключи,
`all` либо отсутствие связей. Внутри ветки действует ИЛИ, между ветками — И.
`team.all` адресует правило всем сотрудникам компании. `project.all`
распространяет правило на любой выбранный проект. Пустая проектная ветка
означает внепроектное знание; оно не попадает в конкретный проект.
Пустая командная ветка означает знание без специального адресата: его можно
читать без выбора команды и с конкретной командой. `all` не выводится из
отсутствия данных: недоказанная применимость остаётся `unknown` для проверки.
При ручном сохранении или утверждении используются только выбранные скоупы:
пустые проекты означают внепроектное знание, а `project.all` выбирается явно.
Отдельного флага или чекбокса внепроектности нет. Пустые обе ветки допустимы;
нерешённые ссылки и зависимости извлечения по-прежнему требуют решения.

| Запрос | Применимость команды | Применимость проекта |
| --- | --- | --- |
| команда T, проект A | T, team.all, без адресата | A, project.all |
| команда T, проекты A и B | T, team.all, без адресата | отдельные группы A/project.all и B/project.all |
| команда T, проекты [] | T, team.all, без адресата | только внепроектные атомы |
| команды [], проект A | team.all, без адресата | A, project.all |
| обе ветки [] | team.all, без адресата | только внепроектные атомы |

`memory.search` доступен агенту и планеру; прямой recall из TurnPreflight
использует тот же Pydantic-контракт аргументов. Выбор проектов для запроса
не изменяет конкретный фокус чата. Они получают сформированный приложением
факт `execution_context`: `team_keys`, известные `project_keys` (включая селектор
`project.all`), `focused_project_keys` и revision. Этот факт не является новой
записью в долговременной памяти и не задаёт права доступа.

Команды всегда берутся полностью из текущего контекста. Их можно передать явно
или опустить `team_keys`; очистка или подмена команд в поиске возвращает
`context_teams_required`. `project_keys` выбираются только из известных проектов:
неизвестный ключ возвращает `project_not_in_execution_context` до поиска.
Отсутствующий список проектов наследует текущий конкретный фокус. Явный `[]`
ищет внепроектное знание; `["project.all"]` — только общие проектные правила,
без перечисления или чтения частных правил всех проектов. Конкретный проект
автоматически включает общие правила. При передаче конкретных проектов вместе
с `project.all` общие правила включаются в каждую проектную группу без отдельного
дублирующего запроса. `team.all` остаётся только привязкой атома, не запросом.

Например, при контексте команд `["team.ops"]` и проектов A/B:
- `project_keys=["project.a"]`: правила команды для A и общие проектные правила;
- `project_keys=["project.all"]`: только общие проектные правила этой команды;
- `project_keys=[]`: внепроектная память этой команды.

`limit` ограничивает каждую проектную группу (1–12 атомов), список содержит
не более 30 ключей. Результат содержит `groups`, а каждый атом сохраняет
`query_scope_keys`, чтобы проектные результаты не переносились между проектами.
Явный запрос общих правил сохраняет свой смысл при дальнейшей проекции контекста.
Ограничения применяются до семантического/лексического поиска и повторно при сборке
ответа. RBAC и доступ к документам остаются отдельными существующими проверками.

Совместимые обязанности компании и проекта действуют одновременно.
Проверка извлечения сравнивает содержание только при пересечении применимости.
Различие названий или текстов само по себе не означает противоречие.
Подтверждённое противоречие конкретного проекта и `project.all` сохраняется
как `scope_override` в существующих `memory_conflict_cases`; на чтении
проектное правило вытесняет только связанное с ним общее правило.
Для найденного правила подтягивается доступная парная сторона такого конфликта,
чтобы семантический лимит не скрыл действующее исключение. Проекты сравниваются
отдельно. Противоречия внутри одной применимости остаются на проверке.

### Извлечение и утверждение

Документ изучается существующим pipeline документной коллекции. Экстрактор
получает активный каталог скоупов и опубликованный глоссарий, разбирает sections
на атомы и предлагает `team_keys`, `project_keys` с основаниями.
`mentioned_scope_keys` хранит простые упоминания и не влияет на применимость.
Неизвестные применимые команды/проекты предлагаются через `scope_proposals`;
основанием служат sections документа. Ссылка на термин необязательна; если она
указана, сначала утверждается термин из того же document/attempt, затем скоуп.
Без зависимости от термина скоуп сразу доступен для проверки. Зависимые атомы
разрешаются только после утверждения их скоупов. Эти зависимости используют существующие staging tables.

Применимость принадлежит claim: `memory_candidate_scopes` хранит предложения,
`memory_claim_scopes` — утверждённые связи. `document_memory_scopes` — подсказки
документа, они не распространяют автоматически скоуп на каждый атом.
`scope_signature` разделяет атомы с одинаковым subject и разной применимостью.
Ссылки на glossary terms объясняют содержание и не являются скоупами.

### Фокус чата

Фокус хранит `team_keys` и `project_keys` независимо. Начальные значения
собираются из подтверждённых фактов `user.team_scope`, `user.project_scope`,
`tenant.team_scope`, `tenant.project_scope`, metadata `team_keys`/`project_keys`.
Приоритет каждой ветки: выбор чата, затем пользователь, затем tenant.
Скоуп-факты читаются отдельно от лимита недавнего профиля: давность факта
и большое число других записей не могут удалить начальную команду или проект.
Явная очистка сохраняется через `suppress_team_default`/`suppress_project_default`
и не подставляет defaults обратно на следующем ходе.

Агент может уточнить команду/проект в диалоге, разрешить имя через `memory.lookup`
и через текущий turn routing уточнить контекст исполнения. Затем `memory.search`
принимает проекты из этого контекста и всегда сохраняет все его команды.
Контекст ограничивает поиск по применимости, а не заменяет права доступа. После завершения хода компактер читает диалог, включая
вопросы агента и ответы/подтверждения пользователя, и корректирует фокус.
Пример, упоминание или неподтверждённый вопрос не меняет выбор.
Отсутствующая ветка в операции компактера сохраняется, `[]` очищает её.
Каталог валидирует идентичности, source references подтверждают provenance,
revision guard защищает запись от опоздавшей параллельной компакции.

Миграция `0179` удаляет универсальный product-маркер, сохраняя его связи через
`project.all`, и добавляет тип проекта. Если существуют конкретные product scopes,
миграция останавливается: их нельзя автоматически объявить проектами заказчиков.

Миграция `0180` разрешает scope proposals без обязательного glossary term;
документное evidence сохраняется.
