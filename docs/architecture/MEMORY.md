# Memory

## Контуры хранения

- Контекст чата хранит текущую цель, выбранные проекты памяти, ссылки на файлы и незавершённую работу. Это revisioned snapshot, а не долговременные знания.
- Диалоговые факты сохраняются в `facts` и `FactObservation`. Владельцы `user` и `tenant` определяют происхождение фактов; они не являются проектами документного поиска.
- Документная LongMemory хранится в постоянном корпусе и отдельных графах HippoRAG. `memory.search` читает только этот контур.
- `runtime_execution_events` — журнал выполнения. Он не является памятью.

Сохранённые `MemoryItem`, `MemoryClaim`, document candidates и их административный review относятся к прежнему механизму. Native `memory.search` не читает эти таблицы и не использует их как fallback. Подтверждённый глоссарий остаётся самостоятельным каталогом без scope.

## Единый каталог scope

Scope идентифицируется уникальным slug: `company`, `nims`, `dcbox`. У него есть ID, название, алиасы и lifecycle status. Выбор команд и проектов двумя независимыми ветками больше не используется. Префиксы `team.` / `project.` и универсальные `*.all` не являются частью нового контракта.

В интерфейсе пользователь выбирает «Проекты для памяти чатов». `company` — обычный scope, а не wildcard и не скрытое расширение поиска на другие проекты. Slug фиксирует идентичность: изменение названия или алиасов не переносит документы в другой индекс.

Общий каталог активных scope доступен авторизованным пользователям через
`GET /memory/scopes`. Этот endpoint независим от коллекций и tenant membership;
его используют профиль, настройки пользователей/тенантов, контекст чата и загрузка
документов. Старые виртуальные Project Memory и «Глобальная память», читавшие
`MemoryItem/MemoryClaim`, удалены из пользовательского каталога и API коллекций.
Исторические данные, glossary и административный review сохраняются, но legacy
административные вкладки `Глоссарий`, `Память` и `На проверке` помечены
deprecated и скрыты из `/admin/memory`. Scope-каталог и LongMemory остаются
действующими разделами. Глоссарий доступен отдельной кнопкой в разделе коллекций
и не выдаётся за коллекцию данных.

В БД сохранены совместимые колонки прежнего review-каталога: `scope_type` фиксирован в `project`, `is_all=false`. Они не задают ветки поиска и не выбираются пользователем. Связи исторических данных остаются по прежним ID.

Документная LongMemory — единая общая память для пользователей портала. `memory.search` не фильтрует документы по пользователю, tenant или ACL источника. Scope — только общий тематический/проектный фильтр по выбранным индексам; он не является границей доступа и не создаёт отдельную память для пользователя или tenant. Обычный RAG и доступ к коллекциям остаются отдельными контурами и применяют собственные ACL.

## Привязка документа

При загрузке в документную коллекцию выбирается ровно один активный scope из каталога. По умолчанию это `company`. Он сохраняется в `document_memory_scopes` и metadata источника. Настройка включения документа в LongMemory остаётся отдельной от выбора проекта.

Удаление scope из админки удаляет его LongMemory записи через durable reindex,
но не удаляет исходные RAG-документы и их привязки к коллекциям. Документы,
которые были привязаны только к удалённому scope, получают явный признак
`scope_unassigned`: после переиндексации они остаются в корпусе документов, но
не участвуют в LongMemory ни в `company`, ни в другом scope. Повторная загрузка
с явным выбором scope снова включает их в индексацию.

Политика `memory_enabled` задаётся в конфигурации коллекции только для коллекций типа `document`. API проверяет это ограничение при создании и обновлении; для остальных типов включить извлечение в LongMemory нельзя.

После normalization готов canonical document. Дальнейшая обработка разветвляется:

```text
extraction → normalization ┬→ chunking → embedding → RAG indexing
                           └→ LongMemory: извлечение знаний → индекс scope
```

LongMemory запускается через долговечную операцию `long_memory_document_operations` в транзакции фиксации результата normalization, если включена политика памяти документа/коллекции. `execute_long_memory_document` читает canonical text и передаёт его со scope worker HippoRAG. Пользователь с правом редактирования коллекции может вручную добавить документ с готовым canonical text через POST или поставить его удаление через DELETE. Оба изменения требуют права редактора; GET статуса доступен пользователям с правом чтения коллекции. Неподготовленный или архивный документ нельзя добавить вручную (409). Успех или сбой автоматической ветки не меняет состояние независимой ветки RAG. Старые post-index outbox-команды поддерживаются только для восстановления уже созданной работы.

RAG и LongMemory публикуют собственные ключи в общей `sources.meta`. Эти ветки могут
работать одновременно, поэтому обновление metadata проходит через общий короткий
publication path: сначала блокируется `RAGDocument`, затем актуальная строка
`Source`; только после этого читается и объединяется текущая metadata. Writer меняет
только принадлежащий ему участок, сохраняя артефакты, memory policy и прочие поля,
записанные параллельными ветками. Блокировки не удерживаются во время S3, model,
HTTP или иных внешних вызовов. Транзакция-владелец фиксирует изменение; общий
helper только делает flush. Запись чанков, артефакта чанков и успешного статуса RAG
публикуется одной транзакцией. Устаревшее поколение ingest или LongMemory не может
опубликовать результат. Финальный результат LongMemory записывается только после
generation-проверки; отсутствие `RAGDocument` и `Source` после успешной операции
удаления ожидаемо и не превращает `delete` в `cancelled`. RAG-события и обновление
сохранённого статуса коллекции отправляются после commit; API коллекции при чтении
пересчитывает актуальный snapshot. Проекция статуса обновляется relay-задачей под
блокировкой коллекции; ошибка обновления повторяется Celery до трёх раз. Отправка
relay после commit и доставка отдельных Redis-событий best effort: ошибки
логируются, но не откатывают обработку документа. Поэтому сохранённый
`Collection.status` может ненадолго отставать; user-facing, runtime-info,
capabilities и admin readiness ответы вычисляют snapshot из актуальных статусов
документов.

Несколько исторических привязок одного документа миграция сохраняет: такой документ попадает в каждый из своих scope. Новые загрузки принимают одну привязку. Документ без привязки, загруженный через другой RAG intake, индексируется в `company`.

## Scope чата

Приложение вычисляет набор до запуска preflight:

```text
наследуемый набор = scope тенанта ∪ scope пользователя
явный выбор чата = замена всего наследуемого набора
```

Дубликаты удаляются; порядок сохраняется: сначала tenant, затем дополнительные user scope. Если оба профиля пусты, начальный набор содержит `company`. Он отображается в контексте чата. Изменения профилей учитываются на следующем ходе, пока чат наследует настройки.

Явный `[]` в чате означает отсутствие документного поиска. Он не восстанавливает defaults и не означает поиск по всему корпусу. `scope_keys=null` в `PUT /chats/{id}/memory-scopes` возвращает чат к наследованию. Запись защищена `expected_revision`; поздний runtime writeback не затирает выбор из интерфейса.

Пользователь меняет свой набор в ЛК (`PUT /profile/memory-scopes`), администратор — в карточке пользователя/тенанта. В чате кнопка «Контекст» позволяет заменить набор или вернуться к настройкам профиля. Поля scope фактов, credentials и RBAC остаются самостоятельными механизмами.

## Поиск: один scope — один набор

LLM-facing аргументы `memory.search` — `query` и необязательный `limit` (1–12). Preflight, planner и агенты используют одну зарегистрированную операцию. Приложение подставляет набор scope чата из `memory_search_scope_keys`; модель не передаёт и не расширяет его аргументами инструмента.

Backend параллельно отправляет отдельный запрос в индекс каждого выбранного scope. Модели разрешаются один раз перед параллельными вызовами. Worker использует отдельный пул поиска (`HIPPO_SEARCH_WORKERS`, по умолчанию 8); запросы к разным графам могут выполняться одновременно. Один native engine защищён от одновременной смены capability и выполнения retrieval.

Ответ содержит `groups`, а не объединённый список `items`:

```json
{
  "backend": "hipporag",
  "group_count": 2,
  "partial": false,
  "groups": [
    {
      "scope_slug": "company",
      "status": "completed",
      "success": true,
      "document_count": 3,
      "items": [],
      "count": 0,
      "source_references": []
    },
    {
      "scope_slug": "dcbox",
      "status": "completed",
      "success": true,
      "document_count": 1,
      "items": [],
      "count": 0,
      "source_references": []
    }
  ]
}
```

Каждый passage содержит текст, score, `scope_slug`, название документа и source references. `index` идентифицирует использованный готовый граф, если он есть.

- Число групп равно числу выбранных scope, в том же порядке.
- `limit` применяется отдельно к каждому scope.
- Успешная пустая выдача сохраняется как группа с `success=true`, `items=[]`.
- Сбой сохраняется как группа с `status=failed`, `success=false`, `items=[]` и безопасными `error_code`/`error`. Он не удаляет успешные соседние группы.
- Ошибка общей настройки модели также возвращает по одной ошибочной группе на scope.
- Пустой набор scope возвращает `groups=[]`, `group_count=0` без вызовов моделей и worker.
- `partial=true`, если хотя бы одна группа неуспешна. Успех tool envelope означает получение групп, а не успех каждой из них.

Объединения, общего rerank и ограничения общего количества passages нет. Runtime-проекции сохраняют границы групп, пустые результаты и ошибки; они не преобразуют их в общую выдачу.

## Хранение и индексы HippoRAG

Worker хранит документы и metadata в `portal-corpus.sqlite` внутри постоянного volume. Добавление документа заменяет прежнюю версию по document ID. Корпус фиксируется только после успешной индексации всех затронутых scope.

Для каждого scope строится отдельный native граф из его документов. Фильтр применяется до retrieval; документы других scope не участвуют в графе поиска. Индекс для комбинации scope чата не создаётся. Графы и кеши зависят от документов и конфигурации моделей, а не от health-check timestamp.

Поиск использует готовый индекс. Он не запускает OpenIE или сборку графа; отсутствие готового индекса даёт ошибку соответствующей группы. HTTP 409 при переиндексации отличается от успешной пустой выдачи.

Кеш извлечения не зависит от `scope_slug`/`scope_slugs`. При переносе документа используется сохранённый split/OpenIE, а metadata привязок обновляется. Записи кешей и snapshot публикуются атомарно, чтобы параллельные поиски не читали незавершённые файлы.

## Выбор моделей и переиндексация

LLM берётся из системного дефолта реестра. Для embedding есть отдельный флаг `models.use_for_long_memory`; частичный уникальный индекс допускает одну выбранную модель. Выбранную модель нельзя удалить или отключить до замены.

Смена encoder в одной транзакции создаёт `long_memory_reindex_requests`. После commit заявка обрабатывается Celery; периодическая reconciliation подхватывает пропущенные запуски и повторяет ошибки до трёх раз. Перед сборкой API передаёт актуальные привязки документов из PostgreSQL. Удалённые из источника документы исключаются из native корпуса.

Переиндексация пересчитывает векторы и графы каждого scope по сохранённым passages/entities/facts, без повторного split/OpenIE. Если извлечение отсутствует, это явная ошибка; LLM fallback в режиме reindex запрещён. Новые и изменённые документы проходят обычный ingest.

## Передача между runtime-ролями

Документная рабочая память принадлежит конкретному исполнителю:

- Планер хранит собственные находки в `runtime_plans.memory_context` между всеми итерациями и репланами одного запуска.
- Каждое задание хранит собственные находки в `runtime_plan_tasks.memory_context`. Повторная попытка и возобновление после подтверждения используют сохранённую память задания.
- Preflight использует свои результаты в пределах собственного tool loop; они не добавляются автоматически в память планера.
- Агентское задание получает общие подтверждённые факты и применимый chat context, но не получает поисковую память планера или соседних заданий. Оно самостоятельно ищет знания под свою задачу.

Результаты `memory.search` дополняют запись `type=document_memory` с отдельной группой на scope. Исходные тексты и provenance сохраняются целиком. Точные дубли определяются кодом по тексту и источнику внутри scope; retrieval score не меняет идентичность фрагмента. LLM-компоновки, пересказа, общего rerank и вытеснения старых находок нет. Ошибка или пустой ответ нового поиска не удаляют ранее найденные фрагменты.

В каждом LLM-вызове текущая накопленная память владельца передаётся один раз. Записи истории вызовов содержат краткие receipts без повторных текстов; полные оригинальные ответы остаются в событиях инструментов. Ограничение контекстного окна модели применяется обычным механизмом LLM-транспорта, без скрытого обрезания документной памяти.

После `needs` текущий протокол создаёт новые task IDs. Для явного продолжения прежней задачи тем же executor планер задаёт `continuation_of` и resolution `continue_with_tasks`, включающую новую задачу в `replacement_task_ids`. Новое задание получает копию памяти исходного задания, отфильтрованную по своему scope. Helper-задачи без `continuation_of` начинают с пустой документной памятью. Совпадение executor само по себе не переносит память. Изменения памяти продолжения не меняют сохранённый снимок исходной задачи.

Каждый фрагмент относится только к своему scope; тематическое совпадение не доказывает идентичность объекта или его текущее состояние.

При явной смене scope preflight передаёт запрос planner: приложение сначала применяет проверенный выбор, затем поиск выполняется уже в новых scope. При возобновлении плана используется сохранённый набор его scope.

Прямой synthesis после preflight получает найденные группы. Для memory-only плана без агентских задач группы также доступны synthesis. Если выполнялись агентские задачи, evidence для planned synthesis составляют их отчёты и источники. Аварийная финализация после ошибки плана не превращает сырые результаты поиска в подтверждённый результат задачи.

После ответа отдельно работают `FactExtractor → FactCompactor → FactReconciler`. Они сохраняют только подтверждённые user/tenant facts; scope поиска и сообщения о выполненных действиях не являются фактами, автоматически записанными в память.

Эти роли относятся только к фактам диалога: `FactExtractor` создаёт кандидаты из
сообщения пользователя и проверенных evidence, `FactCompactor` объединяет или
согласует их с текущими фактами, а `FactReconciler` детерминированно записывает
переходы в `facts`/`FactObservation`. Они не агрегируют найденные passages
LongMemory и не публикуют документные знания в HippoRAG. Документный путь
использует собственный `long_memory_document_operations` worker и native
HippoRAG indexing. Настройки «Изучателя документов» относятся к отдельному
legacy shadow study/review pipeline; вкладка оркестрации скрыта и помечена
deprecated, pipeline/API оставлены для исторических операций.

Финализация фактов и сводки сохраняет payload в `memory_finalize_outbox` до
отправки Celery task. Периодический reconciler повторно отправляет ожидающие и
просроченные jobs; worker делает запись идемпотентной по источникам наблюдений
и отмечает outbox completed только после успешной финализации.

## Наблюдаемость рабочей памяти

`tool_call`/`tool_result` показывают запрос и полный ответ каждого `memory.search`, включая исходные passages, источники, пустые группы и ошибки. После поиска записывается `status(stage=memory_context_used)` с фактическим накопленным контекстом, `memory_owner=planner|task`, `memory_owner_id` и причиной снимка. Начало итерации планера или попытки агента также фиксирует восстановленную память владельца.

Инспекторы планера и агента показывают последний записанный снимок своего контекста с группами по scope. Инспектор инструмента показывает только результат выбранного поиска. Содержимое снимков не восстанавливается чтением текущего корпуса или суммированием дочерних вызовов. Payloads проходят стандартное редактирование секретов и политику уровней журнала.

Миграция `0193` добавляет `runtime_plan_tasks.memory_context` и `continuation_of`; старые задания получают пустую документную память.

## Миграция 0191

- `project.<slug>` становится `<slug>`, `project.all` — `company`.
- `team.<slug>` становится обычным scope `team-<slug>`, `team.all` — `team-common`. Отдельного типа команд больше нет.
- При коллизии slug добавляется стабильный суффикс из прежнего ID. ID и документные/исторические связи сохраняются.
- Профили, scope чатов, metadata источников и активные continuations переводятся на новые ключи. Старые результаты общего поиска удаляются из рабочего контекста активных планов; журнал событий не переписывается.
- Документы без привязки получают `company`. Исторические множественные связи сохраняются.
- Обновляются prompts preflight и chat-context compactor без изменения моделей и таймаутов.
- Создаётся долговечная заявка пересборки отдельных графов из сохранённых извлечений.

API, Celery workers и HippoRAG worker должны быть обновлены совместно. До готовности новых scope-индексов соответствующая группа сообщает ошибку, а не читает старый общий граф. Рабочую production-базу следует мигрировать штатным release-процессом.

## Наблюдаемость и управление документом

Операции добавления/удаления сохраняются в PostgreSQL (`long_memory_document_operations`) без FK на документ, поэтому команда удаления переживает физическое удаление `ragdocuments` и `sources`. `long_memory_generation` документа и generation worker-команды защищают от поздней записи устаревшего добавления. Доставка через Celery повторяется периодической reconciliation; прогресс и попытки сохраняются. Повторный delivery одного operation ID не создаёт параллельную работу в worker. Перезапуск worker переводит незавершённые локальные операции в failed; приложение может доставить их повторно в пределах лимита попыток.

Временные ошибки LLM (timeout, connection, rate limit, upstream), пустые и невалидные структурированные ответы повторяются внутри worker на уровне одного запроса: до трёх попыток с экспоненциальной паузой и учётом `Retry-After`. На этом этапе узел остаётся processing. При усечении по длине бюджет ответа увеличивается в пределах контекста и потолка 4096; все повторы используют единый лимит попыток. Успешные валидированные ответы кешируются отдельно для каждого запроса NER/triples; восстановление документа использует этот кеш. Частичный документ не публикуется как готовый.

Callback передаёт безопасные `code`, `message`, `retryable`, `retry_after_ms` из общего LLM adapter. Ошибка сохраняет стадию и ID чанка; raw provider body и текст невалидного ответа в неё не включаются. Постоянные ошибки (credentials, permissions, unsupported contract, context budget, refusal) автоматически не повторяются. После исчерпания локальных попыток операция становится failed; reconciliation может повторить временный сбой до общего лимита, выдерживая минимум `HIPPO_OPERATION_RETRY_DELAY_SECONDS` (60 секунд) и более длинный provider cooldown. `progress` хранит `retryable`, `error_code`, `retry_after_seconds`, `next_retry_at`; старые записи без этих полей остаются восстанавливаемыми. Повторные Celery delivery также проверяют cooldown и лимит попыток.

Worker ведёт `portal-operations.sqlite` отдельно от транзакции изменения корпуса. Поэтому чтение статуса не ожидает окончания индексации. В документном status graph поле `memory[]` содержит два узла, отображаемых отдельной веткой после normalization:

- `knowledge`: фрагменты, обработанные уникальные фрагменты, сущности из нормализованных троек, уникальные факты, общее число извлечённых троек, использование сохранённого извлечения.
- `graph`: закодированные тексты, векторы из кеша, готовые scope, размеры графов обработанных scope, количество добавленных/удалённых документов. Размеры графов относятся ко всему обработанному scope, а не только к выбранному документу.

Каждый узел содержит status, started_at, finished_at, error и metrics. Статусы публикуются через документный SSE после commit проекции. Статусбар также опрашивает активные процессы, чтобы восстановить пропущенные события. Удаление не требует извлечения знаний: первый узел завершён с `skipped=true`, второй отражает удаление и публикацию обновлённого scope.

Публичные collection endpoints:

- `GET /collections/{collection_id}/docs/{document_id}/memory` — операция и актуальная статистика worker; при недоступном worker availability=unknown.
- `POST .../memory` — поставить в очередь добавление документа с готовым canonical text; для неподготовленного или архивного документа вернётся 409. Доступно редакторам коллекции.
- `DELETE .../memory` — поставить в очередь удаление документа из LongMemory. Настройка документа становится explicit disabled, чтобы следующий автоматический ingest не добавил его снова. Доступно редакторам коллекции.
- Старый `POST .../memory/legacy-extract` — deprecated и возвращает 410.

Удаление из документной коллекции также сохраняет команду удаления из LongMemory. При удалении worker сначала исключает источник из поисковой выдачи, затем удаляет его из активного корпуса и строит оставшийся набор затронутых scope по сохранённым извлечениям. Общие фрагменты и факты других документов сохраняются. Готовность удаления подтверждается завершённой операцией. Старые производные поколения индексов и кеши не являются активным корпусом; их сборка мусора — отдельная эксплуатационная задача.

### Переиндексация LongMemory

Переиндексация отдельного документа не требуется: добавление и удаление документа
обновляют затронутые scope-графы, используя сохранённое извлечение. Полная
переиндексация нужна при смене embedding encoder: HippoRAG пересчитывает
зависимые от encoder векторы и графы по сохранённым passages/entities/facts, без
повторного split/OpenIE и LLM-вызовов. Новые или изменённые документы проходят
обычный ingest. Смена LLM сама по себе не переизвлекает сохранённое знание.

### Административный просмотр HippoRAG

В админской странице «Мемори» LongMemory показывается отдельной вкладкой и не заменяет другие разделы памяти. Список документов постраничный и содержит компактные метрики последней долговечной операции. В карточке документа триплеты извлечения загружаются страницами по 50 записей с позициями в исходном тексте; worker читает snapshot только выбранного документа. Содержимое графа, embeddings, кеши и полный корпус в браузер не передаются.

Проверка поиска вызывает готовый индекс выбранного scope и возвращает не более пяти passages с score и минимальными source metadata. API доступен администраторам; projection ограничивает текст passage и не проксирует произвольную metadata worker-а.
