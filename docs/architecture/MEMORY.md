# Memory

Этот документ описывает реализованные контуры долговременной памяти и их
границы. Это описание текущей системы, не целевая схема.

## Области памяти

В системе есть три независимых вида контекста:

| Контур | Для чего нужен | Хранение и жизненный цикл |
|---|---|---|
| Контекст чата | Ссылки на проекты, файлы, намерения и незавершённую работу внутри одного чата | Типизированный revisioned snapshot; правила в [Chat Context Memory](CHAT_CONTEXT_MEMORY.md) |
| Диалоговые факты | Устойчивые личные и tenant-сведения, подтверждённые по сообщениям и результатам инструментов | `facts` и `FactObservation`; запись асинхронно после синтеза ответа |
| Semantic Memory | Знания о компании и проектах, извлечённые из документов с provenance | `MemoryItem`, `MemoryClaim`, источники, evidence и relations; публикация через документный review pipeline |

Runtime trace хранится отдельно в `runtime_execution_events`. Он не является
источником памяти. Текущее состояние внешней системы всегда получают через
tool, а основания из документов проверяются через RAG.

## Диалоговые факты и глоссарий

После ответа chat-worker запускает `FactExtractor`, `FactCompactor` и
`FactReconciler`. Кандидаты без evidence не публикуются. Подтверждённые
пользовательские и tenant facts попадают в ограниченный runtime snapshot;
Sandbox overlays остаются локальными запуску. Project facts из диалога не
публикуются: проектная Semantic Memory должна происходить из source-backed
документов.

Документный глоссарий (`GlossaryTerm`) хранит только каноническое написание и
aliases. У термина нет tenant, project, определения или уверенности. Определение
из документа извлекается отдельным `description` с собственным evidence,
применимостью и уверенностью. Термины проходят документный staging/review;
админка и runtime читают единый лексический каталог. Старые scoped
`GlossaryEntry`/`GlossaryObservation` сохраняются для совместимости с
диалоговым контуром и историческими данными, но больше не являются каталогом
документных терминов. Старые `GlossaryMeaning` сохраняют прежние определения
для аудита; их нельзя автоматически объявить company knowledge без проверки
применимости и переноса источников в `MemoryClaim`.

## Semantic Memory из документов

1. Для документа действует политика коллекции либо явная настройка документа;
   в metadata также могут передаваться ключи проектов из общего каталога.
2. Активный ingest dispatch запускает shadow extraction. Результаты сохраняются
   как snapshot и кандидаты с ссылками на исходные sections, затем проходят
   conflict check и попадают в административную очередь.
3. Администратор утверждает или отклоняет кандидата. Утверждение термина
   обновляет только написание и aliases; утверждение знания публикует
   `MemoryItem`/`MemoryClaim` с источником, применимостью и видимостью.
   Кандидаты знания с `unknown` и несколькими проектами остаются в review:
   таблица не подменяет неизвестную применимость значением company.
4. Документ можно повторно исследовать; состояние и trace задачи доступны в
   админке. Изменения источника могут сделать прежнее знание устаревшим.

Знания имеют типы `description`, `relationship`, `rule`, `constraint`,
`procedure` и `decision`; glossary terms обрабатываются отдельно. Процедуры и
нормативные типы проходят typed content validation. Состояния semantic item:
`active`, `uncertain` и `stale`.

В коде остаётся старый прямой extraction/publish путь
`runtime/memory/document_memory.py`. Текущий ingest dispatch использует shadow
pipeline; старый worker не считается действующим контрактом и требует удаления
или явного возврата в общий pipeline.

## Чтение в runtime

`memory.search` — единственная публичная system operation для bounded search
долговременной semantic memory и терминов. Она ACL-фильтрует знания по
пользователю, tenant и проектам и возвращает ограниченные результаты с
provenance. Она не предоставляет доступ к таблицам и не отвечает за текущее
состояние внешних систем.

Перед маршрутизацией TurnPreflight получает только механические подсказки
глоссария, проектов и сущностей. При `recall` runtime выполняет ограниченный
поиск и повторно вызывает TurnPreflight; при выполнении planner и агенты могут
вызывать `memory.search` по мере необходимости. Ни один путь не подмешивает
полный дамп памяти.

## Интерфейсы

- Пользовательские «Глоссарий», «Память проектов» и «Глобальная память» —
  read-only виртуальные коллекции, не строки `collections`.
- При загрузке документа можно выбрать политику Semantic Memory и проекты.
  Список проектов является общим корпоративным каталогом; tenant ограничивает
  доступ к документу и его доказательствам.
- Админка показывает глоссарий, опубликованные знания, очередь document
  candidates, конфликты и trace extraction. Изменение semantic content
  проходит через решение по кандидату и источник, а не произвольное
  редактирование опубликованной записи.
- Промпт роли `document_memory_extractor` и настройки этапов доступны в
  Platform Admin.

## Доступ и доказательства

Публикуемое знание связано с документом и section evidence. Tenant visibility
проверяется для content, aliases, relations и evidence. Общий project catalog
не ограничивается tenant; лексические aliases общие. Сейчас видимость
semantic content определяется доступом к source claims. Память является подсказкой с provenance, а не доказательством
текущего состояния системы или разрешением на операцию.

## Типизированные скоупы применимости

Каталог `memory_scopes` содержит стабильный ID, тип (`product`, `project`,
`team`), ключ, название и aliases. Типы ограничены схемой БД; новые значения
каталога администратор создаёт на вкладке «Скоупы». Тип и ключ после создания
фиксируют идентичность, название и aliases можно менять. Миграция `0164` создаёт `product.all`,
`project.all` и `team.all`: каждый ключ означает любое подтверждённое значение
своего типа и не заменяет общекорпоративный `company`.
Существующие проекты получают ключи `project.<project_key>` и связь с прежним
каталогом проектов. Новые проекты, созданные в административном каталоге,
получают такой скоуп сразу; вручную созданный `project.<key>` связывается с
уже существующим проектом того же ключа.

Применимость принадлежит каждому утверждению. `document_memory_scopes`
хранит подсказки документа, `memory_candidate_scopes` — предложенные связи,
`memory_claim_scopes` — утверждённые связи с source claim. Внутри типа
допускается несколько значений (ИЛИ), между типами действует И. `*.all` —
универсальное значение только своего типа. Отсутствие связей у кандидата
означает `unknown`, а у утверждённого legacy claim — явный company scope.

Коллекция определяет политику изучения через `memory_enabled`; скоупы выбираются
для документа отдельно. Документ и его sections дают подсказки экстрактору,
но каждое утверждение проходит собственное разрешение применимости и review.
Неоднозначное или отсутствующее свидетельство не превращается автоматически
в company knowledge.

Изучатель получает только активный каталог. Для каждого утверждения он отдельно
предлагает `scope_keys` применимости и `mentioned_scope_keys` простых упоминаний;
названия без соответствия в каталоге сохраняются для проверки, не создавая
скоупы автоматически. Администратор видит эти предложения и может заменить
применимость перед публикацией. Утверждение записывает выбранные связи в
`memory_claim_scopes` и сохраняет решение в журнале кандидата.

Скоуп можно удалить сразу или пометить на удаление с периодом хранения.
Пометка исключает его из извлечения и чтения; каскад помечает зависимые claims
и память, если у них не осталось применимости через другой скоуп того же типа
или независимого подтверждающего claim. При окончательном удалении связи и
осиротевшие записи удаляются. Восстановление возвращает записи своего каскада.

Tenant загрузки и RBAC источника остаются отдельными измерениями. Сейчас
runtime получает подтверждённые project IDs; конкретные product/team связи
доступны для поиска только при передаче доверенного контекста этих типов.
Старые `MemoryItem`/`MemoryClaim` сохраняют company/project проекцию для
совместимости, но новые ограничения читаются из `memory_claim_scopes`.
`scope_signature` в миграции `0165` разделяет знания с одинаковым subject,
но разными наборами применимости.
