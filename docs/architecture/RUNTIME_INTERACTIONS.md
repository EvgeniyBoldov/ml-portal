# Runtime user interactions

Clarification and confirmation share `RuntimeInteraction`. Runtime creates the
identity, requester and continuation checkpoint; the LLM supplies only a question
and `response_type` (`text` or `boolean`). A question is not a completed answer.

## Public contract

The chat `pause` event and `GET /chats/{chat_id}/paused-run` expose the same
interaction in `context.interaction`:

```json
{
  "id": "interaction-uuid",
  "question": "Какой проект?",
  "response_schema": {"type": "string", "minLength": 1, "maxLength": 4000, "pattern": "\\S"},
  "requester": {
    "stage": "agent",
    "entity_id": "agent-execution-uuid",
    "plan_id": "plan-uuid",
    "task_id": "research-task",
    "agent_slug": "research"
  }
}
```

`stage` is `turn_preflight`, `planner` or `agent`. The runtime binds these fields;
the client cannot choose or override the destination. `response_schema` is the
validation boundary and permits extending answer formats without changing the
pause/resume lifecycle. Current question producers offer text and boolean.

Both chat and sandbox accept the same resume body:

```json
{"action": "answer", "pause_id": "interaction-uuid", "response": "Проект Альфа"}
```

A boolean answer uses the JSON value `true` or `false`. A negative answer is
different from `{"action":"cancel","pause_id":"interaction-uuid"}`, which
cancels the run and its paused plan. For a gated operation, `false` rejects the
operation, cancels that task with `confirmation_rejected`, and returns control
to the planner. For an ordinary boolean question, `false` resumes its requester
with that value. The chat and sandbox provide separate negative-answer and
cancel controls.

The persisted interaction ID must match the response. Wrong types, empty text,
stale answers and repeated deliveries cannot consume a different question.
Legacy `input`/`confirm` requests are transport adapters for existing clients;
new clients send `answer` with a typed `response`.

The Stop button for a currently running chat turn is a separate control request
to `/chats/{chat_id}/runs/{run_id}/cancel`. Closing or detaching its SSE observer
does not cancel the run. The existing `cancel` action on a paused interaction
continues to cancel that paused checkpoint. Persisted chat lifecycle uses the
canonical statuses `running`, `waiting_input`, `waiting_confirmation`,
`completed`, `failed`, and `cancelled`. Runtime stages and action descriptions
are separate transport activity; see [Chat Turn Lifecycle](CHAT_TURN_LIFECYCLE.md).

## Continuation ownership

| Source | Stored checkpoint | Continuation |
| --- | --- | --- |
| TurnPreflight | Original goal, question history, lookup and memory results | Reinvoke TurnPreflight for that goal with the answer; reuse lookup and search results |
| Planner | Original `PlanRequest`, memory results and answered questions | Reinvoke that planner checkpoint in the same plan; skip TurnPreflight |
| Agent | Task identity, working messages, observed tool results/receipts, sources, artifacts and agent version | Reinvoke the same task's LLM with its saved context and answer; skip TurnPreflight and completed tasks |

Planner asks with `PlannerStep(kind="interaction", interaction=...)`. An agent
asks with `completion="interaction"` and the same `InteractionQuestion` object.
Operation confirmation is generated by the tool gate and enters this same
mechanism with a boolean schema plus runtime-owned operation fingerprint.

Execution preparation still checks current permissions and credentials. A
continuation does not use the user's short answer as a new planning goal.
The task agent's published version is pinned by its checkpoint. Successfully
executed tools and their receipts remain in the saved working context; resuming
does not restart the earlier tool loop. An interrupted native tool batch is
stored as completed results plus the not-yet-executed pending operation, without
orphaned native tool-call messages.

## Persistence and transport

Plan and task interactions use `runtime_pauses.payload`. Task status is
`waiting_input`; the running attempt closes as paused/cancelled, and a response
allows a new execution attempt of the same task. A planner pause releases its
planner claim only after the matching response. Root TurnPreflight interactions
need no plan: their checkpoint lives in the paused `chat_turn` or sandbox run.
Migration `0194` extends the task status constraint for these pauses.

Chat and sandbox copy the persisted checkpoint before clearing their pause.
The plan store locks the plan and active pause when consuming a response.
A checkpoint survives a fresh database session and process restart.
Private checkpoint messages are excluded from public chat SSE and paused-run
responses. Clients receive the question, expected answer schema and requester
identity; operation fingerprints remain part of the existing confirmation
action contract, while signed authorization tokens stay runtime-owned.

An approved gated operation still requires the normal signed confirmation token
for the stored user/chat/fingerprint. Token issuance happens before consuming
the transport pause; an issuance failure leaves the question retryable.
The answer never changes the authorized operation or its arguments.

## Policy and observation

`ToolContext.extra.interaction_policy` controls whether a source may ask. The
pipeline initializes it from the same optional platform configuration map.
For example, `{"agent":{"research":false,"default":true},"planner":true}`
denies new questions from `research` without changing the continuation format.
Shadow invocations cannot pause for user interaction. Existing operation
confirmation gates remain mandatory and are not disabled by this asking policy.

Canonical interaction events carry the interaction ID, requester entity and
parent stage. `question_answer` records the typed response against the same
interaction. This keeps the request and response attached to the asking planner
iteration or agent execution in the runtime journal.

## Verification

`test_runtime_interactions.py` exercises the production pipeline, graph and agent
loops with controlled external dependencies. It covers requester-local resume,
typed validation, stale IDs, negative answers, cancellation distinction,
completed-tool preservation and policy denial. It does not replace
`RuntimePipeline.execute` with a scripted E2E harness.
`test_runtime_interactions_pg.py` checks migration and checkpoint/answer
persistence across PostgreSQL sessions in isolated schemas; set
`RUNTIME_INTERACTION_TEST_URL` to an asyncpg SQLAlchemy URL to run it.
