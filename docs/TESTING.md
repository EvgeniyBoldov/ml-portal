# Тестирование

Тесты проверяют контракты на подходящем уровне, а не повторяют один сценарий во всех слоях.

## Где размещать тесты

- Backend unit: `apps/api/tests/unit/`. Проверяют ветвления и инварианты одного сервиса, функции или адаптера; внешние сервисы и БД заменяются предсказуемыми mock/fake.
- Backend integration: `apps/api/tests/integration/`. Проверяют реальные границы между компонентами: HTTP, БД, миграции, очереди и runtime. Для сценария указывайте требуемые сервисы и переменные окружения.
- Frontend unit/component: рядом с исходным модулем в `apps/web/src/` как `*.test.ts[x]`; Vitest и Testing Library проверяют поведение компонента или доменной логики.
- Browser E2E: `apps/web/e2e-tests/` как `*.e2e.ts`. Оставляйте здесь пользовательские критичные цепочки через браузер; мокируйте только дорогие/недетерминированные внешние вычисления, которые не являются предметом сценария.
- Тесты отдельного сервиса размещайте у сервиса. Например, rerank проверяется в `apps/rerank/tests/`, а не импортируется из тестового каталога API.

Не дублируйте один и тот же набор проверок на каждом уровне: unit покрывает правила и ошибки, integration — реальные межкомпонентные контракты, E2E — несколько ключевых пользовательских потоков.

Для архитектурных, API, persistence и межсервисных контрактов выберите focused unit/integration/contract tests, которые проверяют измененный контракт. Такие изменения завершены только после синхронизации документации-владельца и успешного выполнения соответствующих проверок. Если нужный тест не удалось запустить или он упал, укажите это как незавершенную проверку и не объявляйте контрактную работу завершенной.

## Обычный цикл проверки

После изменения сначала запустите узкие тесты затронутого модуля. Затем, перед завершением работы, выполняйте соответствующие полные наборы:

```sh
make test-unit         # backend и frontend unit/component
make test-integration  # backend integration
make test-e2e          # браузерные сценарии Playwright
```

Для диагностики можно запускать один backend-файл из API-контейнера:

```sh
docker compose exec api pytest tests/unit/test_<area>.py -q
```

`make test` сейчас является короткой проверкой unit + integration и требует запущенного dev-стенда. E2E запускается отдельно через `make test-e2e`; для chat contract и live-LLM сценариев см. [`apps/web/e2e-tests/README.md`](../apps/web/e2e-tests/README.md).

## Надёжность тестов

- Не ходите в настоящую БД из unit-теста: подменяйте границу репозитория/сервиса и проверяйте именно контракт тестируемого слоя.
- Не полагайтесь на порядок запуска и состояние контейнера; каждый тест должен сам задавать нужные данные и зависимости.
- Не подменяйте тестируемую логику её же ожидаемым результатом. Для ошибок добавляйте regression test, воспроизводящий наблюдаемое поведение.
- Удаляйте тест только если проверяемый контракт действительно удалён или покрыт новым актуальным тестом. Не удаляйте его лишь потому, что он падает.
- Размещайте тест рядом с компонентом-владельцем и обновляйте его при изменении публичного контракта.
