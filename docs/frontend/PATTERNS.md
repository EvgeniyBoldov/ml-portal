# Frontend Patterns

Практические шаблоны реализации.  
RULES.md отвечает на вопрос «что обязательно», этот файл — «как именно делаем».

## 1) Архитектурный скелет

### App composition

```tsx
<ErrorBoundary>
  <ThemeProvider>
    <QueryClientProvider>
      <AuthProvider>
        <SSEProvider>
          <ToastProvider>{children}</ToastProvider>
        </SSEProvider>
      </AuthProvider>
    </QueryClientProvider>
  </ThemeProvider>
</ErrorBoundary>
```

### Routing

- `'/gpt/*'` — user app
- `'/admin/*'` — admin app
- Admin защищен через `AdminGuard`
- Страницы грузим lazy + `Suspense`

## 2) API pattern

### Один HTTP client

Используем только `shared/api/http.ts`:

- access token в памяти
- refresh через httpOnly cookie
- единый timeout/error/idempotency flow

### Query keys

Только через `qk`:

```tsx
const detail = useQuery({
  queryKey: qk.policies.detail(slug),
  queryFn: () => policiesApi.get(slug),
});
```

## 3) Admin page pattern (целевой)

Используем `EntityPageV2` + `Tab` и собираем страницу из готовых блоков.

```tsx
export function PolicyPage() {
  return (
    <EntityPageV2
      title={policy.name}
      mode={mode}
      onEdit={handleEdit}
      onSave={handleSave}
      onCancel={handleCancel}
      breadcrumbs={breadcrumbs}
    >
      <Tab title="Обзор" layout="grid">
        <EntityInfoBlock entity={policy} fields={fields} />
        <ShortEntityBlock entity={policy} />
      </Tab>

      <Tab title="Версии" layout="full" badge={versions.length}>
        <VersionsBlock versions={versions} onSelect={handleSelectVersion} />
      </Tab>
    </EntityPageV2>
  );
}
```

### Layout choice

- `grid` — overview
- `full` — data tables
- `single` — create/edit forms
- `custom` — сложные исключения

### Admin headers and breadcrumbs

- Все страницы `/admin/*` используют `EntityPageV2` как единственный источник заголовка страницы: H1, подзаголовок сущности, действия и состояние редактирования. Не добавляй второй H1 или отдельный локальный page header.
- Каждая страница задаёт `breadcrumbs`: корневая страница раздела показывает только текущий раздел; создание и карточка сущности показывают ссылку на список и текущий объект; вложенные страницы добавляют сущность и дочерний объект по маршруту.
- Названия крошек совпадают с названиями разделов в интерфейсе, а ссылки ведут на соответствующие родительские маршруты. Для страниц с query-параметром вкладки сохраняй его в ссылке на родительскую вкладку.
- Внутренние вкладки сущности не добавляются в крошки, если они не имеют отдельного вложенного маршрута.
- Для дочерней страницы `EntityPageV2` показывает кнопку-стрелку перед H1 и ведёт на ближайшего предыдущего родителя с href в крошках. Страница раздела без родителя такую кнопку не показывает.
- Булевы поля в блоках сущностей используют общий компонент `Checkbox`; не добавляй нативные браузерные checkbox для полей формы.

### Личный кабинет пользователя

`/gpt/profile` использует собственный layout страницы, а не admin `EntityPageV2`:
сверху заголовок, ниже underline-навигация и карточки на всю доступную ширину.
Все вкладки используют одинаковый фон карточек, рамки, скругления и отступы по
образцу вкладки «Данные рабочей группы»; содержимое остаётся отдельными блоками.
Вкладка «Информация» складывает identity-card и настройки памяти в одну колонку;
каждый блок сохраняет отдельную карточку и естественную высоту. В identity-card
логин — основной текст, роль показывается компактным бейджем, email и дата
регистрации — вторичными полями. Раздел областей памяти держит личные и
значения рабочей группы в отдельных группах; описание говорит, что выборы
объединяются при поиске, а при пустых списках применяется `company`. Блок
параметров рабочей группы доступен только для просмотра.

Раздел «Учётные данные» оформляет личные credentials и API-токены как отдельные
панели. Действие создания располагается в заголовке своей панели, пустое состояние
объясняет следующий шаг. Показывай счётчики credentials и API-токенов только для
успешно загруженного списка соответствующего режима. Для токенов оставь компактный
бейдж общего количества; отдельные метрики статусов не нужны. Статус каждой строки
учитывает `is_active` и `expires_at`. На mobile перед прокручиваемыми таблицами
показывай короткую подсказку о скрытых справа полях и действиях. Примеры команд для
API размещай в закрытом по умолчанию нативном `<details>` с `<summary>`.

Сохраняй четыре раздела и условную видимость управления рабочей группой для
администратора рабочей группы. На узком экране полоса вкладок остаётся в одну строку
с горизонтальной прокруткой и доступом с клавиатуры. Действия размещай в заголовке или панели того
блока, к которому они относятся. Длинные логины и email должны переноситься, не
расширяя страницу. Источник факта показывай локализованным читаемым значением, а
неизвестное значение не выводи в сыром snake_case. Используй общую тему и
spacing-токены. Поскольку GPT layout ограничивает высоту основной области, страница
профиля растягивается внутри неё и владеет вертикальной прокруткой без второго
ограничения `100vh`.

## 4) List page pattern

```tsx
export function PoliciesListPage() {
  const { data, isLoading } = useQuery({
    queryKey: qk.policies.list(filters),
    queryFn: () => policiesApi.list(filters),
  });

  if (isLoading) return <Skeleton />;

  return (
    <DataTable
      data={data?.items ?? []}
      columns={columns}
      onRowClick={(row) => navigate(`/admin/policies/${row.slug}`)}
    />
  );
}
```

## 5) Form pattern

```tsx
const [form, setForm] = useState(initialForm);

const handleChange = (field: keyof FormState, value: string) => {
  setForm((prev) => ({ ...prev, [field]: value }));
};

<Input value={form.name} onChange={(e) => handleChange('name', e.target.value)} />
<Textarea value={form.description} onChange={(e) => handleChange('description', e.target.value)} />
```

Правило: большие формы — page-level, не modal-first.

## 7) State boundary pattern

### React Query

- server data: query/mutation/invalidation

### Zustand

- UI state only (sidebar, toggles, local selections)

## 8) Anti-patterns

- новый кастомный UI при наличии блока в `shared/ui`
- server entities в Zustand
- hardcoded query keys
- shared CSS между admin pages
- бесконечные «временные» EditorPage без плана миграции

## 9) Trace inspector Viewer

Для sandbox trace используем цепочку `trace projection -> Viewer -> Inspector`.
Проекция читает канонические journal relations и создаёт типизированную модель;
Viewer показывает только эту модель в едином стиле; Inspector выбирает сущность и
набор табов. Viewer не выполняет поиск событий, не получает данные и не выбирает
табы. Сложные представления (`PlanViewer`, `LimitsViewer`, `RbacViewer`,
`PromptViewer`, request/response/result viewers) живут в sandbox domain и
переиспользуются между инспекторами. RAW остаётся отдельным read-only табом.

Для каждого типа inspector заранее задай применимые tabs и для каждого tab —
presentation schema: источники в связанных journal events, payload paths,
порядок полей, renderer и поведение при отсутствии значения. Не добавляй в tab
все автоматически найденные данные и не используй generic object-to-fields как
штатный fallback. Новое поле journal безопасно появляется только в RAW, пока не
будет намеренно добавлено в typed tab model.

`Info` показывает краткую идентичность и состояние сущности: type, status,
duration, attempts/calls и компактный usage. Тематические tabs раскрывают один
аспект (`Task`, `Plan`, `Request`, `Result`/`Error`, `Prompt`, `Access`,
`Memory`, `Facts`). Структурные области отображаются специализированными
Viewers; JSON и большой текст — форматированным read-only Viewer с действием
полноэкранного просмотра; статусы и enum-типы — локализованными label/badge.
Необязательное отсутствующее поле скрывается, ожидаемое показывает `Нет данных`,
обязательное — явную ошибку presentation contract.

Вкладка доступа использует отдельные компактные таблицы с колонками «Название»,
«Источник», «Статус» и «Описание». Planner показывает таблицы агентов и тулзов;
agent — источников и тулзов; preflight — тулзов. Для тулза источником служит
название родительского источника, а для системного тулза — «Система»; для агентов
и источников поле источника пустое. Статусы локализуются и показывают RBAC или
Preflight, когда причина блокировки известна. Не подставляй ключи и сырые payload
в поле описания: отображай только `description` из типизированной access-модели,
иначе прочерк. Источник тулза берётся из `source_label`, а при его отсутствии —
из родительского источника или известного системного scope. Для строки агента
используй `agent_description` снимка как fallback, если у элемента нет своего
описания. Значение источника показывай бейджем: DCbox — info, Jira — success,
Confluence — warn, NetBox — danger, «Система» и неизвестные источники — neutral.

Обычный agent inspector использует общий `InspectorTabs`, как planner, и
открывается на `Задача`; `Результат` показывается, если записан результат.
Выбранный tab сохраняется при обновлениях trace той же сущности; при смене tab
открытые полные окна закрываются. Ширину панели задаёт внешний resizable
separator: default 420 px, clamp 320–680 px, с keyboard controls и
сохранением/clamp существующей ширины.

Нормализованный effective
status и время исполнения находятся в общей шапке; отдельный блок ресурсов не
показывается, а повторный таб `Инфо` не добавляется. Вкладка `Лимиты и расход`
сводит фактические входные, выходные и общие токены с записанными лимитами в
одни строки на метрику. Статус учитывает authoritative
lifecycle failure/cancel/pause и business outcome, а не raw coroutine
completion; needs/unfulfillable не показываются как успех. Task variant не
показывает статус задачи и различает незаписанный input и явно переданный `{}`
(«Дополнительных параметров нет»). Непустая цель выбирается из записанной цели,
инструкций или описания без повторения совпадающего текста. Agent-specific
goal, instructions, dependencies и expected result показываются обычным
пропорциональным текстом; только длинные инструкции сворачиваются на месте.
Recorded response format и expected result descriptions отображаются отдельно; planner сохраняет
существующее представление expected outputs. Специализированные planner,
checkpoint и document-memory inspectors сохраняют собственные табы.

Результат агента принимает только нормализованную typed-модель из projection:
Viewer не читает journal и не показывает TaskResult envelope. Секции располагаются
в порядке needs, структурированные данные, файлы, источники и замечания; ответ,
ограничение и interaction сохраняют отдельные подписи. Действия инструмента
показываются в трейсе, без повторения в результате. Пустые
секции скрываются, а `0`, `false`, `null`, пустой объект и список сохраняются.
Needs оформляются карточками с kind и required. Структурированные данные
показываются компактными строками или таблицей; вложенные записи разделяются на
группы. В объекте короткие скалярные значения идут первыми, сложные группы
следом, длинные строки занимают отдельную полноширинную секцию `details`,
закрытую по умолчанию. Остаток длинных списков и записей раскрывается на месте.
Полный просмотр structured data показывает тот же читаемый DataViewer и явный
переключатель JSON; JSON сохраняет исходные ключи и значения. Глубокие объекты
и массивы раскрываются дополнительными уровнями без потери вложенных значений.
Diagnostics агрегируются по известным безопасным кодам и получают пояснение;
произвольные notes остаются в структурированных данных, а технические детали —
в RAW. Источники проецируются полностью; длинные списки показывают
первые десять значений и раскрытие остатка. Известное отсутствие обязательного
файла получает локализованное описание ограничения. Файл строится из artifact id
через `buildArtifactDownloadUrl`; source URL проходит allowlist абсолютных
HTTP(S) без username/password, иначе остаётся текстовой подписью. Envelope
metadata остаётся в RAW, содержательные domain keys и значения не теряются.

Legacy final content разбирается как declaration только при валидном
completion и строгом allowed-field/type shape. JSON без completion или с
дополнительными domain keys остаётся structured data. Sidecar `sources`
проецируется как citation DTO; связь final определяется явными owner links
выбранного agent execution, а не соседством событий.

Вкладка «Доступ» для агента использует две компактные таблицы с названием,
доступом и раскрываемыми описанием/причиной; источник тулза показан бейджем
под названием. «Лимиты и расход» сводит параметр, фактический расход и лимит в
три колонки; расход, лимит, остаток или перерасход видны сразу. Нормальное
состояние выражается шкалой без повторного бейджа «В норме»; предупреждения
и перерасход сохраняют явные метки.
Ограниченный usage bar отображается только при наличии recorded расхода и
положительного лимита. При отсутствии лимита/расхода явно указывается, что
значение не записано; проценты не вычисляются. Поясняющего раскрытия времени
в таблице нет. Память
сгруппирована по областям, не показывает технический owner как редактор, а
открывает факты выбранной группы в читаемом представлении; верхняя карточка
статуса подготовки контекста и суммарных счётчиков не отображается. Промпт отображается
как Markdown-документ с поиском и исходным текстом в полном просмотре;
заголовки внутри fenced code остаются кодом, изображения не загружают внешние
ресурсы. Поиск и действие полного просмотра занимают отдельные строки панели.
RAW показывает свёрнутые события, поиск по ключам/значениям и полный payload.
