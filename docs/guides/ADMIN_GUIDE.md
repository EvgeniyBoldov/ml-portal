# Admin Guide

Гид для platform admin и tenant admin: как устроена система управления, что на что влияет, и где типичные риски.

Сопутствующие практические инструкции:

- [Environment Setup](../admin/ENV.md)
- [Build Guide](../admin/BUILD.md)

## 1. Зона ответственности администратора

Администратор управляет:

- пользователями и ролями,
- tenant-ами и их настройками,
- агентами, политиками, промптами,
- инструментами и инстансами,
- доступами (permissions) и credential sets,
- эксплуатационным состоянием (runs, health, audit).

## 2. Основные сущности и связи

Каждый пользователь состоит ровно в одном tenant-е либо не назначен tenant-у.
В карточке пользователя можно сменить этот tenant; активное членство является
default для аутентификации и sandbox. LDAP-пользователи создаются при первом
входе, а пароль задаётся только локальным учётным записям.

- **Agent**: исполняемый профиль поведения.
- **Prompt/Baseline**: инструкции и рамки.
- **ExecutionLimits**: единая модель лимитов исполнения (platform / orchestrator_role / agent).
- **Tool + ToolInstance**: функциональность и конкретное подключение.
- **PermissionSet**: кто что может использовать.
- **CredentialSet**: какими кредами и на каком scope подключаемся.
- **Collection/RAG**: корпоративные данные для поиска и контекста.

В карточке агента поле «Тип агента» доступно при создании и редактировании:
«Обычный» (`regular`, по умолчанию) или `shadow`. Для shadow сохраняются версии,
публикация, настройка модели и лимитов. Разрешите вызов техническому пользователю
через существующий RBAC; его Bearer access token используется для
`POST /api/v1/agents/shadow/invoke`. Shadow не предлагается планеру и в выборе
агентов чата. Первый режим — LLM без инструментов и памяти, с JSON-ответом;
запуски видны в текущем инспекторе согласно уровню логирования.
[Контракт shadow API](../architecture/AGENT_RUNTIME.md#shadow-api-invocation).

## 3. Scope и приоритеты

Критичный инвариант: разрешение идет по цепочке:

1. user
2. tenant
3. default

Приоритет всегда: **User > Tenant > Default**.

Это влияет на:

- доступы к инстансам/инструментам,
- выбор кредов,
- итоговый runtime-контур пользователя.

Личный список проектов документной памяти пользователь настраивает в своём
профиле, а общий список рабочей группы — администратор рабочей группы в своём ЛК.
Чат наследует объединение обоих наборов, а явный выбор в чате заменяет
его целиком. При пустых профилях выбирается `company`. Изменения профиля
применяются на следующем ходе унаследованного чата.
Каталог состоит из активных slug без веток команд/проектов и wildcard.
При загрузке документа выбирается один проект, по умолчанию `company`.
LongMemory общая для пользователей портала: native `memory.search` не фильтрует
документы по пользователю, tenant или ACL источника. Scope выбирает индекс из
общего корпуса и служит для организации тематического поиска, а не для выдачи
или ограничения доступа. Обычный RAG и коллекции применяют собственные проверки.
Миграция `0191` переносит старые ключи с сохранением ID и ставит пересборку
scope-индексов в долговечную очередь. Обновляйте API, Celery и HippoRAG worker
совместно; подробности — [Memory](../architecture/MEMORY.md).

## 4. Роли и ограничения

## 4.1 Platform Admin

Может:

- управлять всей платформой,
- менять default настройки,
- управлять системными сущностями глобально.

Риски:

- изменение default scope может затронуть всех пользователей.

## 4.2 Tenant Admin

Платформенный администратор назначает администраторами тенанта пользователей
из состава тенанта. Администратор тенанта работает в своём ЛК и может:

- добавлять credentials тенанта;
- назначать редакторов данных из участников тенанта;
- управлять скоупами тенанта.

Не может:

- менять глобальные системные настройки,
- управлять чужими tenant-ами.

Tenant admin может изменять содержимое коллекций своего tenant-а. Для той же
возможности можно назначить участнику роль редактора данных. Platform admin без
одной из этих ролей в целевом tenant-е не получает право записи содержимого только
за счёт platform-роли. Конфигурация, схема и источники коллекций остаются в
platform control plane.

Флаг платформенного администратора даёт доступ к админке. Роли администратора
рабочей группы и редактора назначаются отдельно в членстве пользователя в группе.
В карточке пользователя платформенный администратор может менять имя, логин,
почту и пароль только для локальной учётной записи; LDAP-профиль управляется
провайдером идентификации. В карточке рабочей группы назначаются её администраторы.

## 5. Где что настраивается в админке

- `Настройки платформы -> Лимиты`
  - только platform-level execution limits (LLM + Runtime).
- `Оркестрация -> Planner / Memory / Synthesizer / Fact Extractor / Fact Compactor`
  - у каждой системной роли свои execution limits (LLM + Runtime) и свой prompt contract.
- `Память` (facts)
  - runtime memory имеет scopes `user`, `tenant`, `project`;
  - администратор может просматривать и редактировать факты через отдельные
    user/tenant surfaces, но credentials никогда не входят в memory и не
    показываются через memory API;
  - автоматические изменения проходят `FactExtractor -> FactCompactor ->
    FactReconciler`, а ручные admin edits помечаются как manual и используют
    supersede/tombstone semantics;
  - ошибки асинхронного memory writeback не отменяют уже выданный ответ.
- `Агенты -> <агент> -> Лимиты`
  - execution limits конкретного агента (LLM + Runtime).
- `Настройки платформы -> Политики/гейты`
  - policy gates (`forbid_*`, `require_confirmation_*`) и policy text.

Важно:
- лимиты исполнения больше не ведутся через platform caps;
- единый источник лимитов — `execution_limits`.
- `LLM таймаут (сек.)` задаёт ожидание одного вызова модели; более узкий
  scope имеет приоритет над platform default.

## 6. Операционный минимум (ежедневный контроль)

### Дашборд `/admin`

Главная страница показывает использование за последние 1, 7 или 30 суток и
текущее состояние моделей, документных RAG-коллекций и проектов HippoRAG.
Статистика обновляется раз в минуту; график группируется по часам/дням UTC.
Запрос — отдельный runtime run чата или Shadow API; продолжение того же run
после уточнения/подтверждения не увеличивает счётчик. Песочница исключена при
записи и чтении статистики. Фоновые операции индексации не входят в обращения.
Активные пользователи — уникальные авторы обращений за период; запуски агентов
включают повторные попытки. Доля ошибок считается среди запросов со статусами
`completed` и `failed`, без ожидающих ввода и отменённых.

API `GET /api/v1/admin/dashboard?days=7` доступен только platform admin.
Компактный учёт `platform_usage` не зависит от уровня диагностического журнала,
не содержит текстов/результатов и не удаляется семидневной очисткой трасс.
Повторная доставка lifecycle-событий обновляет запись по идентичности;
LLM-попытки разделяются. Токены провайдера и оценочные токены отмечаются отдельно;
отсутствующий usage не становится нулём. Учёт модельных вызовов охватывает LLM
runtime чата и Shadow API; вызовы embedding/reranker и фоновой индексации пока
показываются через назначения и состояние, без счётчиков вызовов.
Дата начала полного учёта хранится в `platform_usage_coverage` (миграция `0203`).
История до её применения не восстанавливается из неполных журналов; интерфейс
отмечает неполный период, сравнение появляется при наличии обоих полных периодов.

RAG показывает текущие документы, чанки и объём исходных файлов по коллекциям.
Объём не включает индексы/кеши; один документ может входить в несколько коллекций.
HippoRAG группируется по активным проектам памяти. Worker отдаёт только компактную
статистику опубликованных scope-индексов через внутренний
`GET /portal/corpus/statistics`, без загрузки графа и вызова моделей. Для старого
графа без сохранённой статистики число узлов/связей неизвестно до следующей
загрузки графа. Недоступность worker не блокирует остальные блоки дашборда.

В таблице документов отдельно показаны агрегированный статус RAG с сохранённым
числом чанков и готовность LongMemory. Статус LongMemory считается готовым только
когда завершены извлечение и индексация; их этапы и документные метрики
(фрагменты, триплеты, факты, сущности) отображаются раздельно. Размер берётся из
исходного файла, принадлежность к проекту — из сохранённых областей документа.
Если счётчик отсутствует в API, интерфейс показывает, что данных нет. Действия
строки, включая удаление, находятся в меню рядом с названием; массовые действия
остаются в панели выбранных документов.

«Требует внимания» объединяет недоступные назначенные модели и включённые
подключения, ошибки/частичную готовность RAG, ошибки/отсутствие индексов памяти,
долгую обработку без обновлений и повторяющиеся ошибки моделей/агентов периода.
После последующего успешного вызова модели или запуска агента соответствующая
группа ошибок исчезает из проблем, сохраняясь в статистике периода.
Ожидание пользователя и штатная обработка не являются проблемами.
Пороги задаются `DASHBOARD_HEALTH_STALE_SECONDS` (3600),
`DASHBOARD_STALLED_DOCUMENT_SECONDS` (3600) и
`DASHBOARD_REPEATED_ERROR_THRESHOLD` (3). Устаревшая проверка модели даёт
«Неизвестно». Назначения моделей отражают текущую конфигурацию; использование —
фактические вызовы периода. Дашборд не запускает проверки и переиндексацию.

1. Проверить `runtime_execution_events` с `event_type=error` и terminal executor outcomes.
2. Проверить health tool instances.
3. Проверить ошибки ingestion/RAG pipeline.
4. Проверить изменения прав/кредов в audit.

Если где-то много красного — сначала стабилизируем, потом улучшаем. Не наоборот.

## 7. Типовые административные сценарии

## 7.1 Выдать доступ пользователю к инструменту

1. Проверить роль и tenant пользователя.
2. Обновить PermissionSet на нужном scope.
3. Проверить effective permissions.
4. Прогнать тестовый запуск агента.

## 7.2 Подключить новый tool instance

1. Создать/обновить ToolInstance.
2. Добавить credential set на нужном scope.
3. Проверить health status.
4. Привязать instance к агенту (binding) и проверить policy limits.

## 7.3 Включить новый источник данных

1. Создать/настроить collection или RAG ingestion.
2. Убедиться в корректности schema/metadata.
3. Проверить поиск и фильтрацию по tenant/scope.
4. Открыть доступ через PermissionSet.

## 8. Lifecycle удаление (soft/hard)

- Любая сущность lifecycle сначала может быть переведена в `deprecated` (soft delete).
- Hard delete доступен отдельно, опционально с каскадным удалением зависимостей.
- Перед удалением нужно смотреть граф зависимостей (что удалится, что перепривяжется).
- Физическое удаление deprecated-сущностей выполняется фоновым GC по retention TTL.

## 9. Правила безопасных изменений

- Не менять несколько контуров сразу без проверки.
- Любые изменения прав/кредов — с проверкой effective access policy и scope-правил (tenant = отдел, не жёсткая SaaS-граница).
- Изменения политик — только с оценкой влияния на SLA/стоимость.
- Все критичные изменения должны быть обратимыми.

## 10. Эскалация и взаимодействие

Передавайте в AI engineering, если:

- нужен новый tool handler,
- требуется изменение runtime flow,
- есть системная деградация качества/latency,
- есть повторяющиеся ошибки в ingestion/tool execution.

Админка — это пульт управления, а не генератор сюрпризов. Лучше маленький контролируемый шаг, чем большой героизм в пятницу вечером.

### Карточка модели: подключение и характеристики

Карточка модели разделяет основную информацию, подключение и характеристики
конкретного типа. Для LLM отображаются версия и контекстное окно; для embedding —
версия, размерность и лимит текста; для reranker — версия и лимит пары
запрос/документ. Размерность у reranker отсутствует. Настройки таймаута и повторов
свёрнуты в дополнительный блок; повторы на этой странице доступны для LLM.
Служебные идентификаторы и даты находятся на отдельной вкладке.

«Проверить» при создании и редактировании обращается к текущему подключению
формы без сохранения записи. Каждая полученная характеристика становится
доступной только для чтения. Отсутствующие значения можно заполнить вручную;
неизвестная версия не блокирует сохранение. При сохранении нового снимка
backend повторно получает metadata сервиса, чтобы не доверять клиентскому
JSON как источнику характеристик. Изменение подключения сбрасывает предыдущий
снимок. В режиме просмотра проверка обновляет сохранённые характеристики и
health. Задержка проверки означает время проверки доступности сервиса, а не
длительность embedding/rerank inference.

### Переход существующих коллекций на отдельные embedding-индексы

Примените миграции 0186 и 0187 до обновления конфигурации моделей. Они добавляют
характеристики моделей и фиксируют совместимость старого энкодера; коллекции
Qdrant при этом не удаляются. Обновляйте API и workers согласованно: старые
workers не должны продолжать писать в прежний общий индекс.

Проверьте embedding-модели в карточках: необходимы настоящие размерность и
лимит входа. Затем выполните `POST /api/v1/admin/rag/reindex/run?dry_run=true`
(при необходимости с `tenant_id` и `model_alias`) и проверьте список документов.
Повторите запрос с `dry_run=false` для постановки в существующий durable ingest
pipeline. Каждый запрос ограничен `limit` (1–500). После окончания пачки
повторяйте dry-run до отсутствия устаревших кандидатов. Документы возобновляются
с embedding по сохранённым каноническим чанкам; при отсутствии чанков
используется существующий полный ingest fallback.

Табличные коллекции перевекторизуются своим обычным механизмом. Смена набора
моделей или характеристик переводит строки в pending, даже если до этого
необработанных строк не было. Изменение порядка тех же моделей не требует
перевекторизации. Предыдущие поколения сохраняются; автоматическое удаление
при переключении модели отсутствует. Аудит коллекций учитывает поколения.

До завершения backfill покрытие новых индексов может быть частичным.
Совместимые старые документные точки читаются только с проверкой модели,
версии и размерности; для индексов без достоверной привязки нужен reindex.
Обновление health/latency не является причиной reindex. HippoRAG остаётся
отдельным хранилищем и использует собственный энкодер LongMemory.

### Использование модели и состояние сервиса

«Включена» (`enabled`) — административный допуск к использованию записи модели
платформой. Он учитывается при выборе LLM, embedding и reranker, а также
энкодера LongMemory. Выключение не останавливает сервис модели и не удаляет
индексы. Проверка подключения и metadata остаётся доступной. Уже начатая
операция не является гарантированно отменённой после выключения.

Таблица моделей показывает отдельно использование (включена/выключена), статус
модели в реестре и health сервиса с задержкой последней проверки. Работающий
сервис может быть выключен для использования платформой. Назначение «По
умолчанию» сохраняется у выключенной записи, но не делает её доступной для
выбора; поведение замены зависит от потребителя. Явно заданная выключенная LLM
не подменяется другой записью через кэш имени провайдера. Для отключения
текущего энкодера LongMemory сначала требуется выбрать другой энкодер.
