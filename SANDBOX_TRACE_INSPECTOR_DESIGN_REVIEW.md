# Sandbox Trace Inspector: текущие нерешённые findings

Дата проверки: 2026-11-07. Объект: [sandbox](http://nginx:8080/sandbox/a20d2b9c-e000-4f9c-a11c-acb780d67988), trace 247 с, 194 события, executor `inventory.netbox`, tool calls `netbox_get_objects` и `result.load`.

## Проверка и свидетельства

- Chromium: URL выше, HTTP 200, заголовок «Почемучка», ошибок страницы нет. Штатный capture открыт при 1440×1000; файл: `apps/web/test-results/visual-review/20261107-084310Z-new-sandbox-current.png`. Live capture показывает общий trace и финальный ответ; inspector в нём не выбран.
- Выбранные inspector состояния сверены по скриншотам этого run при 1440×1000: `new-sandbox-tool-call-info.png`, `new-sandbox-tool-call-response.png`, `new-sandbox-result-load.png`, `new-sandbox-agent-prompt.png`, `new-sandbox-access.png`, `new-sandbox-readiness.png`.
- Prompt у `inventory.netbox` предписывает проверять `source_complete/source_total` и вызывать `result.load`, если источник неполон. В trace видна последовательность `netbox_get_objects` (50 из 72) → `result.load` (`mode=remaining`, 22 строки) → следующий `result.sql`. Поэтому факт отсутствия инструкции в prompt этим запуском не подтверждается.

## Подтверждённые findings

### P1 — «Ответ» дублирует метаданные stored result и не связывает дозагрузку

**Наблюдение:** у `netbox_get_objects` в «Ответе» сначала показано «Результат сохранён отдельно · строк в результате: 50», затем в разделе «Данные» повторены 50 и 72. Аналогично у `result.load` повторено число 22. Оба ответа сообщают, что полные данные не входят в событие; кнопка «Показать сведения о результате» относится к сохранённому результату, но текущий viewer не показывает полный набор строк. В списке trace `result.load` выглядит отдельным tool call, а в его «Ответе» видны только 22 строки, всего 72 и признак неполной обработки источника; связь с предыдущими 50 строками не сформулирована.

**Эффект:** пользователь может принять два значения «строк в результате» за разные объёмы данных, а число 22 — за полный результат вместо оставшейся части. Путь от первой выборки к дозагрузке приходится восстанавливать по соседним элементам trace и prompt.

**Рекомендация:** оставить одно компактное резюме для каждого call: `50 из 72; источник обработан не полностью` и `загружено ещё 22; режим remaining`. В trace связать вызовы короткой подписью продолжения («Загружены оставшиеся 22 из 72»). Не обещать просмотр полного набора, пока viewer раскрывает только payload события; полное содержимое требует штатного Result Store browsing.

**Статус:** дубли и отсутствие явной связи подтверждены скриншотами; рекомендации по формулировкам — дизайн-предложение. Само наличие данных в Result Store и полнота backend-страниц этим визуальным проходом не проверялись.

### P2 — «Доступ» повторяет identity выбранного агента

**Наблюдение:** в inspector executor `inventory.netbox` вкладка «Доступ» показывает строку `Агент inventory.netbox — Разрешено — Разрешён runtime RBAC`, а также разрешённую коллекцию `netbox`. Над таблицей есть сообщение «Коллекции без явного правила: разрешены».

**Эффект:** строка про самого исполнителя дублирует identity в заголовке inspector и может читаться как доступ агента к самому себе; полезная информация о доступных ресурсах смешана с техническим решением RBAC.

**Рекомендация:** в обычном представлении оставить ресурсы/операции и причины ограничений. Решение RBAC по агенту показывать только если оно объясняет отказ или отдельное решение доступа; иначе поместить в раскрываемые технические детали. Сохранить ясное объяснение правила коллекций без явного правила.

**Статус:** содержимое вкладки подтверждено; необходимость скрывать строку зависит от продуктового назначения вкладки и требует решения владельца домена.

### P2 — успешная «Готовность» занимает отдельную вкладку, но показывает технические счётчики

**Наблюдение:** у executor вкладка показывает «Проверка завершена», режим `full`, 18 доступных операций, 1 подключённый источник данных и общее сообщение, что необходимые операции, коллекции и авторизация отмечены доступными. Конкретные проверенные операции и источник не перечислены. Смысл результата пересекается с «Доступом».

**Эффект:** пользователю неясно, что означает режим `full` и какие именно условия готовы; успешное состояние занимает отдельное место без следующего действия. Числа сами по себе не объясняют готовность этого запуска.

**Рекомендация:** успешный итог свернуть в статус/строку на «Инфо» или «Доступ», если отдельная вкладка не нужна по контракту. Отдельное подробное состояние оставить для блокеров: назвать недоступную операцию/источник, причину и следующий шаг. Если вкладка остаётся, расшифровать `full` и обозначить область проверки.

**Статус:** показанные поля и пересечение с «Доступом» подтверждены скриншотом; перенос/сворачивание — рекомендация, требующая проверки продуктового контракта readiness.

## Рамки этой ревизии

Эти findings относятся только к указанному sandbox/run и видимым состояниям inspector. Визуально проверены общий экран и состояния tool info/response, `result.load`, prompt, access и readiness при 1440×1000; мобильный размер, клавиатура/focus и другие outcome-состояния не проверялись. Предыдущие замечания, уже исправленные в реализации, удалены из этого документа. См. также правила trace inspector в `docs/frontend/PATTERNS.md`.

## Дизайнерский комментарий к предложениям по структуре inspector

Предложения, переданные из исходного чата: связать обновление Result Store; объединить «Доступ»; убрать отдельную «Готовность»; пересобрать «Инфо» и «Задача». Формулировки здесь восстановлены по резюме предложений в истории, поэтому ниже оцениваю именно этот смысл.

### Предлагаемая структура вкладок

- **Инфо** — выбранный объект, его статус и контекст выполнения. Для executor: агент/роль, статус, длительность и компактные счётчики с явно обозначенным scope; одно короткое состояние preflight, только если оно есть в trace.
- **Задача** — цель executor-а и существенные входы/ожидаемый результат, если они присутствуют в журнале. Не повторять идентичность, статус и общие счётчики из «Инфо»; attempts и дочерние calls оставить в дереве trace.
- **Доступ** — решения доступа к коллекциям/источникам/операциям, с причиной и субъектом проверки. Для run-scoped readiness показать здесь только блокирующие access findings, если это действительно одно и то же решение.
- **Результат** — итог выбранного шага или call. Для stored result: доступный preview и полнота; переход к сохранённому набору должен быть явным и показывать границу между event payload и Result Store.
- **RAW** — исходные технические данные и диагностические связи.

«Промпт», «Лимиты», «План» и тематические вкладки оставить условными: показывать, когда у выбранной сущности есть соответствующий материал. Это удерживает главный сценарий — понять задачу, состояние и результат — впереди диагностических подробностей.

### Оценка предложений и trade-offs

1. **Связать обновление Result Store с исходным вызовом — поддерживаю.**

   **Подтверждённые факты trace/UI:** видны `netbox_get_objects` с 50 из 72, затем `result.load` в `remaining` с 22, после него ещё один tool call. В prompt есть инструкция проверять полноту и дозагружать результат. Текущий inspector показывает calls отдельными элементами и дублирует счётчики в «Ответе».

   **Дизайнерское мнение:** отразить это как продолжение в дереве/результате исходного call — «первые 50 из 72» → «добавлено ещё 22» → последующий запрос, если его связь подтверждена trace. Учитывать, что `result.load` может быть отдельной пользовательски значимой операцией: не скрывать исходный call и не сливать два event payload в один фиктивный ответ. Если связь не подтверждена журналом, показывать только соседство и метку «возможное продолжение», не утверждать причинность.

   **Компромисс:** единая линия понятнее для пользователя, но требует надёжной связи/агрегации событий и аккуратного показа частичных ошибок. До появления backend-подтверждения интерфейс не должен выдавать `source_total` за число уже загруженных строк или обещать полный просмотр Result Store. Сам экран не доказывает, какой API читает полный сохранённый набор.

2. **Объединить «Доступ» с «Готовностью» — объединять только блокирующие решения, а не данные целиком.**

   **Подтверждённые факты:** текущая вкладка «Доступ» показывает разрешение runtime RBAC для `inventory.netbox` и разрешённую коллекцию `netbox`. «Готовность» показывает `full`, 18 доступных операций, 1 источник данных и общий успешный итог. Экран показывает пересечение тем, но не доказывает, что readiness и RBAC вычислены одним backend-решением или имеют одинаковый срок действия.

   **Дизайнерское мнение:** объединённая вкладка может быть проще, если в ней чётко разделены группы «Доступ к данным» и «Проверки запуска», а готовые проверки сведены к короткой строке. При ошибке показать конкретный блокер, объект и следующий шаг. Если проверки readiness не являются access-проверками, не называть их «Доступом»; оставить readiness кратким состоянием в «Инфо» и раскрывать причины там, где возник блокер.

   **Компромисс:** объединение уменьшает число вкладок и дублирование, но размывает различие между политикой доступа и проверкой конкретного запуска. Пользователю важно понимать, является ли разрешение постоянным правилом, а готовность — снимком preflight для этого run. Данные экрана недостаточны, чтобы подтвердить временную/семантическую модель backend.

3. **Убрать отдельную «Готовность» — поддерживаю удаление отдельной успешной вкладки, но не потерю её результата.**

   **Подтверждённые факты:** в этом run проверка успешна; показаны технические счётчики и общее сообщение. Конкретные операции/источники и значение `full` в UI не раскрыты.

   **Дизайнерское мнение:** положительный итог можно свернуть в «Инфо» (например, «Preflight пройден») или в группу проверок доступа, если это корректно по контракту. Сохранить отдельное видимое состояние при блокере/ошибке и раскрываемую диагностику. Не удалять вкладку без проверки, что readiness может содержать полезные не-ACL блокеры: иначе пользователь потеряет объяснение, почему запуск невозможен.

   **Компромисс:** меньше навигационного шума при успехе; возможно, больше кликов при диагностике. Если readiness — самостоятельный объект или имеет собственный жизненный цикл, отдельный inspector может быть оправдан, но текущий скриншот этого не устанавливает.

4. **Пересобрать «Инфо» и «Задача» — хорошее направление при жёстком разделении идентичности и содержания.**

   **Подтверждённые факты:** текущая пара скриншотов executor показывает заголовок `inventory.netbox`, prompt с Identity/Mission/Scope и структуру trace с этапами/попытками. Полный состав текущей вкладки «Задача» в предоставленных кадрах не виден, поэтому дублирование её полей нельзя считать подтверждённым.

   **Дизайнерское мнение:** «Инфо» отвечает «кто/что это и в каком состоянии», «Задача» — «что требовалось выполнить и с какими содержательными входами». Prompt — системные инструкции и ограничения модели; не копировать его целиком в Task. Показывать длинный prompt только в отдельной тематической вкладке/раскрытии. Итог, попытки и tool calls не повторять в Task, если они уже доступны в дереве и «Результате».

   **Компромисс:** лучшее разделение снижает повтор и помогает начать с цели выполнения, но может потребовать выбора между более коротким Task и полным prompt. Для диагностики полного контекста оставить доступ к prompt и RAW; отсутствие поля в журнале обозначать как отсутствие данных, не сочинять ожидаемые значения.

### Граница между backend-фактами и дизайн-решением

Backend/journal факты в этой ревизии ограничены тем, что отображено для конкретного run: имена calls, числа 50/72/22, `mode=remaining`, readiness counts/status, видимое RBAC-разрешение и текст prompt. Утверждения о том, что вкладки семантически дублируют один backend contract, что `result.load` гарантированно продолжает конкретный call, что «Готовность» можно удалить без потери иных блокеров, или что весь Result Store можно браузить из текущей кнопки — не подтверждены этим визуальным аудитом. Это требует проверки backend/API контракта.

Рекомендации по группировке, названиям вкладок, сворачиванию успешной readiness и визуальной связи partial results являются дизайнерским мнением для проверки продуктовой командой; они не являются утверждениями о текущей реализации.
