# Текущее состояние памяти и lookup

**Срез анализа:** 30 сентября 2026. Описание runtime и локальной БД ниже отражает состояние на момент анализа. Раздел «Реализованная целевая фаза» фиксирует изменения, внесённые после анализа.

**Актуальное состояние:** 1 октября 2026. Замечания F1–F9 исправлены; этап B реализован и повторно проверен. Первоначальное [ревью от 1 октября](#ревью-от-1-октября-2026-и-план-двух-этапов) ниже сохранено как история обнаруженных проблем. Последний раздел фиксирует дополнительные исправления этапа B и границы проверки. Рабочая БД остаётся на 0174; новые миграции в неё не применялись.

## Кратко

В системе есть четыре отдельных контура контекста:

| Контур | Назначение | Чтение в runtime |
| --- | --- | --- |
| User/tenant facts (`facts`) | Устойчивые пользовательские настройки и факты о tenant | Загружаются при старте turn; подтверждённые записи проходят через `MemoryService` и `FactStore` |
| Контекст чата (`chat_memory_items`) | Рабочая область одного чата: проекты, термины, цель, решения, открытые вопросы, ссылки на файлы и результаты | Загружается отдельным bounded snapshot и передаётся turn и планеру; агентам передаётся проекция |
| Semantic Memory (`MemoryItem`/`MemoryClaim`) | Документные знания о компании и проектах с источниками и ограничениями применимости | Читается через ACL-aware `memory.search` |
| Глоссарий (`GlossaryTerm`) | Канонические корпоративные термины, алиасы и определения из опубликованных документов | Механический поиск помогает маршрутизации; `memory.search` возвращает определения и источники |

Основной пробел для дальнейшей работы — общий контракт подбора: **что искать, в каких scope, откуда scope взялся, и как результат передаётся между turn, планером и агентом**. Существующие механизмы полезны, но их область действия и передача контекста разнятся.

## Как сейчас выполняется turn

1. До маршрутизации `MemoryBuilder` читает подтверждённые facts текущего пользователя и tenant. В facts включаются записи без supersede, затем они ограничиваются по числу и размеру для prompt. В памяти также есть query-aware ранжирование facts для секции `MemoryBundle`; это отдельный путь от `planner_memory_context`, который получает preflight и планер.
2. Runtime разрешает контекст проекта: явные совпадения с каталогом в запросе, затем scope проекта из чата, затем пользовательский default `user.project_scope`. Проектный default содержит ключи проектов в metadata факта.
3. `MechanicalLookupService` ищет точные совпадения терминов и проектов в исходном запросе. Он возвращает ID и совпавшие aliases, без значений долговременной памяти. Поле `entities` сейчас всегда пустое.
4. TurnPreflight выбирает один маршрут: synthesis, planner, recall или clarification. Для recall он формирует `MemoryRequest`, runtime вызывает `memory.search`, затем повторно вызывает preflight с результатом.
5. Если turn уходит к планеру, планер может вызвать `memory.search` до трёх раз и сохраняет результаты внутри текущего planner invocation. Во время выполнения задач агенты имеют собственный инструмент `memory.search`.
6. После ответа факты и chat context обрабатываются отдельными writeback-контурами. Чатовый термин может сохранить ссылку на подтверждённый glossary term, но чат не публикует и не меняет определение.

Детали реализации находятся в [Runtime Memory](docs/architecture/RUNTIME_MEMORY.md), [Memory](docs/architecture/MEMORY.md), [Chat Context Memory](docs/architecture/CHAT_CONTEXT_MEMORY.md) и [Корпоративном глоссарии](docs/GLOSSARY.md).

## Текущая модель scope

Здесь важно разделять три измерения:

- **Владелец контекста:** конкретный чат, пользователь или tenant.
- **Доступ к источнику:** можно ли этому пользователю прочитать документный claim. Для Semantic Memory это проверяется по видимости документа и claim.
- **Применимость утверждения:** к какому проекту, продукту или команде относится знание. Она хранится на связях `memory_claim_scopes`.

Например, tenant может определять доступ к документу, а `team.ops` — область действия правила из документа. Это разные проверки. Наличие project/team/product scope само по себе не выдаёт доступ к исходному документу.

Проверка применимости для typed scopes уже поддерживает логическую схему **ИЛИ внутри одного типа и И между типами**: `(project.a OR project.b) AND team.ops`. `product.all`, `project.all` и `team.all` означают любое подтверждённое значение только соответствующего типа. Отдельно существуют company знания и пользовательские/tenant facts.

В runtime конкретные scope keys передаются через `context_scope_keys`. Текущие вызовы поиска этот параметр не передают. Project scope частично подхватывается через список `project_ids`; product/team scope так не разрешаются. Схемы turn и планера сейчас разрешают в параметре `scopes` только `glossary`, `project`, `global`, хотя сервис поиска умеет категории `product` и `team`.

Это означает, что расширить набор строк в запросе недостаточно. Для product/team нужно определить trusted resolver конкретных ключей и передавать их поиску. Такие ключи должны подтверждаться контекстом пользователя, чата или текущей задачи, а не извлекаться из простого упоминания команды в документе или запросе.

## Реализация целевой фазы

После исходного анализа добавлены миграции `0176`/`0177` и review flow для document memory:

- извлечение выдаёт связанные term и scope proposals; память с предлагаемым scope блокируется до публикации термина и утверждения scope;
- при утверждении термина scope proposal переводится на стабильный `glossary_term_id`, сохраняя исходный candidate для аудита;
- отклонённый candidate или scope можно использовать как feedback следующего извлечения; повтор запускается кнопкой в review UI;
- каждая попытка имеет собственный cursor, feedback и ID; Celery tasks проверяют, что попытка ещё активна;
- повторная попытка supersede-ит неутверждённые кандидаты и предложения старой попытки, сохраняя отклонения для аудита;
- в lookup добавлен ограниченный каталог typed scopes; `MemoryRequest` и planner/agent `memory.search` принимают `scope_keys` с `inherit`/`replace`, включая пустую замену без project fallback;
- выбранные turn scopes передаются в planner и agent context и сохраняются в chat focus как typed `scope_keys`.

Это реализация основы scope handoff, но пока не полного ранжирования: lookup возвращает bounded каталог scope identity (key/name/aliases), а поиск объединяет lexical и semantic кандидатов. Отдельного reranker, адресного facts lookup и query-aware выбора user/tenant facts здесь ещё нет. Проектный resolver всё ещё считает совпадения имени проекта в запросе явным проектным контекстом; его нужно отдельно изменить, если продукт решит отделять упоминание проекта от намерения искать по нему.

## Что сейчас не хватает в выборе памяти

### 1. Область поиска не является единым явным результатом

`ProjectContextResolver` разрешает только проекты и использует порядок:

1. проект явно назван в запросе;
2. иначе используется проект из chat context;
3. иначе — проектный default пользователя.

Focus чата также хранит `project_keys`, но не typed product/team scopes. Для команды и продукта нет аналогичного resolver, который выдавал бы нормализованные ключи, источник каждого ключа и неоднозначности. Нужна общая модель effective scope с происхождением, например: `project=chat focus`, `team=user/team membership`, `product=explicit request`.

Также надо различать *упоминание* scope и *выбор области задачи*. Если пользователь просит сравнить два проекта, оба проекта могут быть релевантны. Их знания следует разделить по проектам, а не свести к одному default или смешать молча.

### 2. Facts пользователя и tenant доступны только стартовым срезом

Факты извлекаются по owner и сначала упорядочены по `observed_at`. `MemorySnapshot.planner_context()` конкатенирует user facts перед tenant facts и применяет общий лимит. При большом профиле пользовательские записи могут вытеснить tenant facts. Query-aware `FactSelectionPolicy` существует для секции `MemoryBundle`, но не используется для стартового `planner_memory_context`.

`MemorySearchService` facts не ищет; переданный в него `user_id` сейчас не участвует в запросе. Поэтому preflight/планер/агент не могут по требованию адресно запросить, например, «default Jira project» или факт о предпочтительном формате, если запись не попала в начальный срез.

Полезная целевая модель: небольшой обязательный профиль для маршрутизации и отдельно адресный facts lookup с owner scope (`user`/`tenant`), subject/kind, текстовым запросом и ограниченным числом результатов. User и tenant значения должны возвращаться с явной меткой источника и противоречиями, а не объединяться в один неразличимый список.

### 3. Найденная память не переносится единообразно по ролям

- Recall из turn передаётся во второй вызов preflight; для прямого synthesis его результат также есть в контексте synthesizer.
- Если после recall выбирается planner, этот результат не добавляется к `planner_memory_context`.
- Поиск самого планера сохраняется только в `memory_tool_results` его текущего вызова. При следующей итерации планер может искать заново.
- Агент получает память, если она включена планером в задачу, либо агент сам вызвал `memory.search`.
- `_task_memory_context` проецирует общий chat context, однако `AgentExecutor` явно отображает `memory_recall` и элементы с `subject`/`value`; project/chat context не имеет отдельного рендеринга там. Переданный агенту список ограничен первыми 12 элементами.

Нужен явный handoff найденной памяти: выбранные утверждения, основания выбора, scope и source references должны связываться с конкретной задачей/iteration и передаваться дальше с ограниченным бюджетом. Это поможет различать, что уже проверялось планером и что агент должен искать сам.

### 4. Lookup слабее последующего поиска

`MechanicalLookupService` сопоставляет написание проекта и термина с canonical name/aliases в исходном запросе. Он не возвращает определения; они появляются в `memory.search`. Lookup не использует aliases для product/team scope и пока не разрешает entities. Glossary match лексический: точное совпадение названия или alias с границами слова; семантического поиска по определению терминов нет.

У chat context есть `term_bindings`, ссылающиеся на опубликованный glossary ID. Это хороший источник закреплённого значения термина в конкретном чате. Стоит сделать binding первым сигналом для разрешения местоименного или сокращённого упоминания, сохраняя возможность сообщить о конфликте с другим значением в текущем запросе.

У механического lookup есть ещё контрактная нестыковка: он передаёт в TurnPreflight `project_context`, `chat_context` и `recent_dialogue`, но действующие правила роли в БД перечисляют разрешённые источники как `user_request`, `mechanical_lookup`, `facts_context`, `continuation` и `recall_context`. Необходимо согласовать промпт с фактически переданным контекстом, чтобы роль могла явно использовать чатовый scope и bindings.

### 5. Результат поиска не полностью объясняет scope и полноту

По умолчанию пустой `project_keys` означает наследование `fallback_project_keys`. Это удобно, но не позволяет выразить «снять scope чата и искать шире». В ответе `search_scope` отражает direction, entity IDs и kinds, но не effective project keys, product/team keys, их происхождение и режим наследования.

И векторные, и лексические кандидаты ограничиваются до ACL/applicability фильтрации. На большом корпусе релевантная запись нужной команды может не попасть в первую ограниченную выдачу до проверки scope. Пустой результат не различает: совпадений не нашлось, корпус не содержит доступных claims, scope не совпал или кандидаты не попали в bounded shortlist. При этом причина должна раскрываться безопасно и не сообщать о существовании недоступных данных.

Для планера и инструмента агента стоит определить единый вход:

- `query` и желаемые типы: facts, knowledge, glossary;
- конкретные scope keys и источник их разрешения;
- режим scope: наследовать контекст задачи, заменить его или явно расширить;
- фильтры kind/entity и лимит.

Ответ должен показывать effective scope, найденные утверждения, provenance, ambiguities и безопасную диагностику неполноты. Для нормативных правил и процедур неоднозначность scope лучше сохранять как неоднозначность, а не подменять широким поиском без явного решения.

## Согласованные идеи развития

Идеи зафиксированы по итогам обсуждения 30 сентября 2026. Часть очереди уже реализована; описание исходного состояния выше остаётся срезом на дату анализа.

### Реализованная целевая фаза: извлечение и утверждение связанных сущностей

**Статус после ревью:** реализована основа; фаза требует исправлений перед включением. Результаты проверки и ближайший шаг приведены ниже.

- Извлекатель создаёт кандидаты терминов и долговременной памяти, связывает утверждения с существующими скоупами или предлагает новые. Для скоупа сохраняются тип, имя, aliases, термин-основание и ссылки на фрагменты документа.
- Новый скоуп, основанный на новом термине, остаётся `awaiting_term`. После утверждения термина он становится доступным на проверку скоупа. После утверждения скоупа все связанные утверждения получают подтверждённую связь.
- Утверждение памяти с `applies_to` на предложенный скоуп заблокировано, пока скоуп и его glossary term не активны. Упоминание (`mentions`) такой блокировки не создаёт.
- Связанный с термином уже существующий активный скоуп связывается автоматически после утверждения термина: отдельное повторное утверждение записи каталога не требуется.
- Модалка показывает неизменяемое содержание, связи, источники и причины блокировки. В очереди у кандидата только отдельные действия «утвердить» или «отклонить»; отклонение требует причины. Массовые approve/delete/deactivate endpoints для staging-кандидатов удалены.
- Скоупы утверждаются в отдельной очереди. Предложение нельзя утвердить до термина; отклонение скоупа блокирует связанные утверждения памяти.
- Схема добавлена миграцией `0176_memory_scope_proposals`.

Ограничение фазы: новая модель scope и термино-связей используется в извлечении и публикации кандидатов. Runtime lookup, передача effective scope между turn/планером/агентами и поиск фактов пользователя/tenant остаются отдельной работой ниже.

### Ревью реализации и ближайший шаг

Запущены существующие тесты извлечения, публикации glossary term, staging-моделей, scopes и источников кандидата: **21 прошёл, 1 упал**. Падающий `test_shadow_bulk_approval.py` проверяет удалённый массовый маршрут; контрактный тест надо заменить проверкой нового поведения. Полный цикл новых scope proposals этими тестами пока не покрыт. Локальная БД остаётся на ревизии **0174**; миграция 0176 не применена.

Обнаруженные дефекты:

1. **Повторное извлечение термина из другого документа может оборвать обработку.** `MemoryScopeProposal.memory_scope_id` объявлен уникальным, но код создаёт отдельное предложение для нового term candidate на тот же существующий scope. Второе предложение нарушит уникальность.
2. **Неоднозначные aliases выбирают первый scope.** `_persist_scope_proposals` использует `next(...)`, хотя aliases могут совпадать у нескольких scope одного типа. Нужно сохранять неоднозначность и блокировать утверждение до корректного извлечения.
3. **Дубликаты становятся недоступны для утверждения в UI.** После удаления автоутверждения duplicate case остаётся открытым. API включает любой открытый case в `conflict_ids`, а модалка блокирует любой такой ID. Следует различать duplicate, compatible_extension и блокирующее противоречие, согласовав API и UI.
4. **Зависимость от утверждённого термина нестабильна.** Предложение хранит `term_candidate_id`, а проверка требует, чтобы это был текущий `GlossaryTerm.approved_candidate_id`. Повторная публикация термина переключает candidate ID и ломает ожидание старых предложений. После утверждения нужна стабильная ссылка на glossary term с сохранением отдельной ссылки на исходный кандидат для аудита.
5. **Ledger не передаёт предложенные scope следующим секциям.** В ledger попадают только связи с активным каталогом. Следующим batch нужны открытые предложения, связанные термины и устойчивые IDs, чтобы агент переиспользовал найденные области.
6. **Отклонение пока не замыкает цикл извлечения.** Причина сохраняется, но отклонённые кандидаты исключены из ledger, а повторное изучение того же checksum переиспользует snapshot без нового попыточного цикла. Нужен явный повторный запуск с замечаниями, новыми кандидатами и сохранением прежних решений.

**Предложенный ближайший шаг:** довести фазу до полного цикла «извлечь → проверить → отклонить с причиной → повторно извлечь → утвердить зависимости → опубликовать память». Сначала исправить пункты 1–4 и покрыть их сценарными тестами, затем дополнить ledger и повторное извлечение. Проверить миграцию на отдельной тестовой БД и полный сценарий с двумя документами, одним термином, одним scope и несколькими утверждениями памяти. После этого переходить к trusted scope resolver и использованию term↔scope в runtime lookup.

### Извлечение терминов, long memory и связей агентом

Статус: основа реализована; остаются замечания ревью выше.

Первым шагом пересмотреть извлечение: агент извлекает из документа термины и долговременные знания, связывает их между собой и со scope, затем передаёт законченные кандидаты на утверждение.

Для каждого кандидата нужны содержание, документные свидетельства, предложенные связи и объяснение применимости. Агент сопоставляет найденные области с существующим каталогом, предлагает новые scope при наличии основания и сохраняет неоднозначность, когда сопоставление не удалось. Упоминание scope и применимость знания к нему должны различаться.

Новый scope проходит как предложение с типом, названием, aliases и источником. Предложения повторно сопоставляются с активным каталогом по типу и нормализованным названию/aliases и переиспользуют открытое предложение того же термина и scope.

### Проверка: утвердить или отклонить

Статус: основа реализована; блокировки дубликатов требуют исправления.

На этапе проверки доступны два решения: утвердить или отклонить подготовленный кандидат. Добавление новых пунктов памяти, ручная дописка содержания и ручное исправление связей/scope должны быть перенесены в процесс извлечения.

При отклонении сохраняется причина, которую получает агент при повторном извлечении. Это позволит исправлять содержание и связи с учётом замечаний проверяющего.

### Реранкер для поиска памяти

Добавить reranker, оценивающий доступные и применимые кандидаты относительно текущего запроса и задачи. Для правил, процедур и описаний учитывать, какой тип знания нужен участнику runtime.

Векторизация памяти уже реализована. Её дальнейшее использование обсудить по дополнительной пользе на реальных запросах вместе с лексическим поиском и reranker.

### Используемость и полезность фактов

Добавить сигналы фактического использования и актуальности: время последнего использования, число задач с использованием факта, время последнего подтверждения и оценку полезности для задачи. Попадание факта в prompt само по себе не считается использованием.

Отбор должен учитывать релевантность, актуальность, используемость и confidence. Более используемые и недавно подтверждённые факты получают больший вес; важные defaults сохраняют гарантированное место в стартовом контексте. Этот отбор нужно подключить к фактическому пути подготовки контекста turn и планера.

### Термины глоссария могут обозначать scope

Позволить термину глоссария явно связываться со scope. Например, термин «Платформа X» даёт определение и aliases, а связанный `product.x` задаёт область применимости знаний. Lookup сможет разрешить название и предложить соответствующую область поиска.

Связь должна быть явной: не каждый термин обозначает область применимости. Агент предлагает связи терминов, знаний и scope вместе с документными свидетельствами.

## Приоритет работы

1. **Извлечение и связи term/scope — реализована основа.** Исправить неоднозначные сопоставления, повторное извлечение термина и стабильность зависимости от glossary term; дополнить ledger предложенными scope.
2. **Модалка утверждения — реализована основа.** Содержание read-only; доступны утверждение и отклонение с обязательной причиной. Исправить блокировку дубликатов и согласовать её с API.
3. **Повторное извлечение по замечаниям — осталось.** Причина отклонения сохраняется, но пока не подмешивается автоматически в следующий запуск изучения того же документа.

Reranker, используемость фактов и применение связей терминов со scope в runtime lookup остаются в плане дальнейшего развития. Их порядок и конкретные контракты предстоит определить отдельно.

5. После этого улучшать кандидатообразование, ranking и диагностику пустого/неполного поиска по измеримым trace данным.

### Замечания к пункту 1

**F1 — P0: цикл зависимости term → scope замыкается в UI.**

Для нового термина со `scope_type` extraction создаёт его собственный scope proposal и связь `applies_to`. `_candidate_approval_blockers` возвращает для term блокировку «Ожидает утверждения скоупа», а модалка отключает approve. Scope при этом ждёт утверждения этого же термина. Серверный approve term такую зависимость не требует, поэтому API и UI расходятся. Воспроизведено прямым вызовом blocker-функции.

Точки: [создание собственной связи](apps/api/src/app/runtime/memory/shadow_document_study.py#L452), [блокировки термина](apps/api/src/app/api/v1/routers/admin/semantic_memory.py#L305), [модалка](apps/web/src/domains/admin/components/MemoryReviewDialog.tsx).

**F2 — P0: обязательный scope может исчезнуть, не оставив запрета публикации.**

Если `term_subject` не найден, `_persist_scope_proposals` записывает только unmatched name и делает `continue`: входной `global` остаётся глобальным, зависимости нет. При нескольких совпавших scope записывается unmatched name, но кандидат остаётся `scoped`; наличие другого корректного scope binding может позволить утвердить неполную применимость. `unmatched_scope_names` также используется для простых упоминаний, поэтому нельзя блокировать по любому unmatched name — нужен отдельный структурированный unresolved `applies_to`.

Воспроизведены обе ветки: отсутствующий term оставляет `global`, неоднозначный required scope оставляет `scoped`, новых proposal bindings нет. Точка: [сопоставление proposals](apps/api/src/app/runtime/memory/shadow_document_study.py#L459).

**F3 — P0: защита от старой задачи и повторной доставки batch неполная.**

Worker сначала загружает snapshot в session, а после LLM читает его с `FOR UPDATE` без принудительного обновления ORM-объекта. Identity map может вернуть прежний `active_attempt_id`; такой повторный SELECT не доказывает актуальность. Перед записью также не сравнивается актуальный cursor с cursor, для которого вызывался LLM: два сообщения одной попытки могут обработать одну секцию дважды. Exception/checksum ветки меняют snapshot без единого guarded transition; сообщения без `attempt_id` принимают текущую попытку. Это особенно важно при `acks_late`/повторной доставке.

Точки: [проверка перед persist](apps/api/src/app/workers/tasks_shadow_document_memory.py#L383), `study_shadow_document_sections`, `finalize_shadow_document_study`. ORM-поведение воспроизведено; полный конкурентный сценарий ещё не прогнан.

**F4 — P0: legacy `project_keys` обходят scope ceiling.**

Search проверяет ceiling до разрешения project keys и проверяет только typed `scope_keys`. При ceiling `project.a` запрос `project_keys=['b']` проходит, выбирает проект B и вызывает recall. Также одновременно заданные `scope_keys=['project.a']` и `project_keys=['b']` не отклоняются как противоречие. Это обход ограничения применимости задачи; сам по себе он не обходит отдельный ACL источников. Воспроизведён реальным вызовом search с замоканными read dependencies.

Точка: [ceiling и project resolution](apps/api/src/app/runtime/memory/search.py#L57). Пустой `replace` действительно отключает fallback, а widening через typed keys действительно отклоняется — эти две ветки работают.

**F5 — P1: повтор использует resolved term candidate как ещё не утверждённый термин.**

`term_candidate_ids` включает resolved terms предыдущих попыток того же snapshot. Если имя найдено в этой карте, lookup опубликованного glossary term не выполняется. Новый scope proposal становится `awaiting_term`, хотя термин уже утверждён; повторный approve resolved candidate не вызывает activation. Получается зависшее предложение. Воспроизведено созданием нового scope proposal с candidate ID уже опубликованного термина.

Точки: [карта term candidates](apps/api/src/app/runtime/memory/shadow_document_study.py#L340), [приоритет term source](apps/api/src/app/runtime/memory/shadow_document_study.py#L459).

**F6 — P1: миграционный rollback не готов к реальным данным.**

В downgrade 0177 сначала удаляется `attempt_id` из scope proposals, затем удаляется индекс этой колонки. PostgreSQL удаляет зависимый индекс вместе с колонкой; следующий `DROP INDEX` завершится ошибкой. Ещё до этого возврат старых CHECK/UNIQUE нарушится на новых `superseded` строках и нескольких proposals одного scope — это штатные данные новой версии. Backfill также относит `queued/screening/studying/conflict_checking` к `completed`, что не отражает реальный attempt lifecycle.

Точка: [миграция 0177](apps/api/src/app/migrations/versions/0177_memory_extraction_attempts.py). SQL generation прошла, применение/rollback на отдельной PostgreSQL БД осталось проверить.

**F7 — P1: retry ещё не является надёжным durable workflow.**

Endpoint делает commit, затем вызывает Celery `.delay`: сбой очереди оставит snapshot `studying`, и следующий retry будет запрещён. Причины отказов выбираются по всем попыткам без IDs/ограничения размера. Кнопка повторного извлечения держится в локальном React state и пропадает после перезагрузки страницы. Attempt status не проходит все terminal transitions вместе со snapshot. Trace run/stage IDs по-прежнему относятся к snapshot и cursor, поэтому несколько попыток смешиваются в одном execution tree.

Точки: [retry endpoint](apps/api/src/app/api/v1/routers/admin/semantic_memory.py#L572), [review UI](apps/web/src/domains/admin/pages/MemoryPage.tsx), `reextraction_feedback`, `_trace_entity_id`, `_update_snapshot`.

**F8 — P1: проверка конфликтов не видит предложенную применимость.**

`ShadowMemoryReviewService._scope_keys` читает только активные `MemoryCandidateScope`. Разные pending scope proposals дают одинаковый пустой набор, поэтому classifier может спутать их с одной областью. Результаты duplicate/compatible extension теперь создаются как resolved, но существующие старые open cases не нормализованы, а API/UI по-прежнему считают любой open case блокирующим. Ledger передаёт proposal ID/type/name/status/role, но не term source/subject, которые нужны следующей секции для повторного предложения той же связи.

**F9 — P1: новый chat scope сохраняется и очищается непоследовательно.**

`replace=[]` работает внутри поиска, но reducer не пишет scope update при пустых explicit keys: chat focus остаётся прежним и вернётся на следующем turn. Topic compaction/reconciler сохраняет прежние `project_keys`/entity refs, но не новый `scope_keys`, поэтому может стереть product/team focus. Кроме того, model-selected keys записываются как `application_verified` без единого resolver перед writeback.

Точки: [reducer](apps/api/src/app/services/chat_context_reducer.py#L16), [reconciler](apps/api/src/app/services/chat_context_reconciler.py#L119), [выбор planner scope](apps/api/src/app/runtime/pipeline.py#L641). Замечание основано на ветках кода; существующие chat-тесты новый typed scope сценарий не покрывают.

2. **Lookup возвращает кандидатов scope через названия и term↔scope.** Сопоставлять key/name/aliases, подтверждённый glossary term и явную связь `MemoryScopeGlossaryTerm`. Возвращать matched forms, основания и неоднозначности. Искать кандидатов относительно задачи; текущие первые 120 строк каталога по алфавиту не являются выборкой релевантности и могут скрывать нужный scope. При ограничении результата обозначать truncation, предусмотреть адресный lookup. Только active published entities участвуют в разрешении.
3. **Turn отдельно выбирает область задачи.** Scope decision должен быть частью общего результата turn для любого маршрута, включая synthesis/clarify, а не только `TaskBrief`/`MemoryRequest`. Механическое совпадение даёт candidate, после чего turn определяет применимость по goal/direction. Runtime проверяет выбранные IDs/keys и происхождение через resolver. Clarification нужна только при неоднозначности, влияющей на ответ. Простое упоминание scope не переключает focus и не делает его default.
4. **Полный chat focus lifecycle.** Хранить только validated selection с provenance по типам. Частичное изменение типа не стирает остальные типы; explicit replace/clear меняет focus согласно заявленному режиму. Compaction не меняет выбранные identities. Snapshot/reducer/reconciler/UI показывают одинаковые scope и source. Archived scope обнаруживается на чтении и не используется как действующий.
5. **Передача в planner iteration и agent task.** Передавать EffectiveScopeContext и выбранную память в PlanRequest; закреплять turn ceiling в durable plan/checkpoint. У каждой задачи хранить собственный scope subset и объяснение выбора, валидируемые compiler. Agent ToolContext получает scope своей задачи. Следующие planner iterations и resume восстанавливают его из сохранённого контракта. Результаты turn recall передаются planner; lookup одного planner invocation не теряется при следующей итерации.
6. **Общий контракт `memory.search` и trace.** Все роли используют единый resolver параметров, ceiling и диагностики. Ответ содержит effective scope по типам, source/provenance, unknown/ambiguous keys, основания исключения и источники найденных знаний. Ceiling ограничивает применимость задачи, ACL независимо ограничивает доступ к claims. Выбор scope виден в trace до recall и при handoff конкретной задаче.

**Критерии завершения B:**

- Запрос про «правила команды X» через glossary alias предлагает и выбирает её scope; простое упоминание команды не переключает focus.
- Неоднозначный alias даёт candidates и, когда требуется, clarification; pending term/scope не используется как active.
- Новый turn может заменить scope или очистить его; chat сохраняет корректное состояние после compaction и на следующем turn.
- Приоритет работает отдельно для project/product/team; новый scope одного типа не расширяется старым default того же типа.
- Два выбранных проекта сравниваются с раздельными источниками/результатами, а не смешиваются в неразличимое правило.
- Planner/task/agent не расширяют ceiling ни через typed keys, ни через legacy project keys; task subset переживает checkpoint/resume.
- Recall от turn доступен planner и его задачам с source references; effective scope и handoff видны в trace.

Порядок реализации: **A1 → A2 → A3 → A4 → A5 → проверка A → B1 → B2/B3 → B4 → B5 → B6 → проверка B**. Reranker и адресный facts lookup остаются следующими самостоятельными этапами.

## Этап B — scope selection и передача памяти в turn/planner/agent — 2026-10-01

Этап B реализован в коде. `EffectiveScopeContext` задаёт выбранные scope identities, отдельные упоминания, режим, provenance, revision и ceiling. Turn preflight сопоставляет выбранные и упомянутые области с активным каталогом; неподтверждённые термины/области не используются. Изменение типа области заменяет только этот тип при `inherit`, а `replace` очищает прежний выбор. Chat reducer/reconciler сохраняют typed keys, их происхождение и явный clear.

Planner получает общий scope context и результаты turn recall. `memory.lookup` ищет активные scope/glossary identities по имени и alias, не раскрывая значения memory; planner `memory.search` и агентский `memory.search` применяют scope ceiling. Planner может сузить или очистить область отдельной задачи; compiler отклоняет widening и требует объяснение для явного выбора. Результаты поиска сохраняются в plan вместе с выбранной областью, восстанавливаются при resume, передаются задачам и фильтруются по применимости scope. Synthesis получает только результаты, видимые в scope плана. Для legacy plan с уже созданными итерациями, но без сохранённого scope context, resume прекращается с `scope_context_missing`, поскольку старый выбор восстановить достоверно нельзя.

Выбор области, task handoff и planner memory lookup отражаются в runtime trace. Проверка применимости выполняется отдельно от ACL: совпадение scope само по себе не даёт доступ к чужим facts.

## Повторная проверка этапа B и исправления — 2026-10-01

При повторной проверке обнаружены ошибки, которые первоначальные 43 unit-теста не покрывали. Они исправлены:

1. **Передача памяти агенту.** Agent prompt раньше игнорировал `planner_memory_result`, а правила из `memory.search` содержали `content`, хотя renderer ожидал `value`. Теперь агент получает найденные statements, процедуры, scope keys и IDs источников; поисковые результаты не теряются после первых 12 user facts. Scope конкретной задачи включён в prompt.
2. **Согласованность recall и финального выбора.** Pipeline теперь ищет по нормализованному effective scope, без fallback из механически упомянутых проектов. Если повторный preflight меняет область, recall и финальное решение выполняются заново; разрешены максимум три прохода. Несовпадение области результата и запрошенной области останавливает передачу памяти. Повторное применение одного выбора в planner-ветке удалено.
3. **Фильтрация всей структуры evidence.** Task/synthesis projection фильтрует не только верхние `items`, но и вложенный `memory_context`, проекты и references источников. Уточнение области также убирает uncertainty о расхождении, относящемся только к исключённым знаниям. `*.all` трактуется как в read-side applicability: требуется конкретное значение того же типа.
4. **Разные области и формулировки.** Read-side recall разрешает claims по группам применимости, включая legacy project/tenant applicability, и сохраняет отдельные формулировки/источники. Scope precedence больше не выбрасывает все расходящиеся правила или произвольно выбирает первое из них. Legacy project applicability переводится в typed keys до handoff, чтобы scoped claim не стал глобальным при фильтрации задачи.
5. **Хранение planner reads.** Ключ результата учитывает операцию и все параметры поиска. Неуспешные reads не сохраняются как evidence. Лимит в 30 результатов ограничивает историю поиска, сохраняя исходные user/tenant facts, turn recall и project context. Проверка `rag_required`/`tool_required` перед synthesis учитывает также результаты planner search. Накопленная история не может сорвать готовый ответ переполнением synthesis context: лишние reads удаляются при compaction с явным флагом truncation.
6. **Защита task scope.** Проверка subset выполняется и в compiler, и на границе сохранения iteration. Явный пустой ceiling не восстанавливается через fallback. Task scope хранит собственный ceiling и rationale; операции агента учитывают этот потолок, включая `memory.lookup`.
7. **Chat focus и resume.** User project defaults не превращаются в явный chat focus при сохранении области. `replace` только на team/product также отключает восстановление project default. Удалённые/устаревшие scope keys очищаются при следующем сохранении focus. На resume восстанавливаются сохранённые scope, origins, default suppression и память плана; после выполнения именно этот scope проецируется обратно в chat focus.
8. **Единый контракт выбора.** Shared и legacy scope selections нормализуются и проверяются на противоречия; неизвестные или не сопоставленные с запросом keys ведут к clarification. Принудительные маршруты fact write и collection inventory сохраняют выбранный scope.
