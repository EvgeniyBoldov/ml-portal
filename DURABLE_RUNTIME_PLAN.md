## 1. Результат для пользователя

Пользователь упоминает бота в треде и поручает задачу. Одно исходное поручение создаёт один приватный чат портала, один логический turn и один root run. Бот возвращает уточнения, подтверждение приёма, содержательные обновления и итог в исходный тред. Задача может завершиться сразу, ждать ответа человека, спать до заданного времени или чередовать работу и сон. После перезапуска API, воркера или бота пользователь продолжает тот же диалог.

Контрольный пример — «Следи за заявкой до завтра 18:00. Сообщи, когда изменится статус». Если номер неизвестен, TurnPreflight спрашивает его у пользователя. Планер поручает агенту первую проверку, фиксирует наблюдение и назначает следующую. После пробуждения поручает свежую проверку, сравнивает её результат с предыдущим и решает, сообщить ли об изменении, продолжить наблюдение или закончить. Следующая проверка, следующая публикация и предельный срок поручения имеют разный смысл. Пользователь может отменить задачу во время ожидания.

Первая версия поддерживает пробуждение по времени и существующие пользовательские ответы. Проверка изменения в источнике выполняется по расписанию, выбранному планером. Push-события источников можно позднее подключить к тому же механизму сигналов. Выбранный адаптер первой версии — Копатыч в Clouds для eXpress BotX.

## 3. Владельцы состояния

**ChatTurn** задаёт публичное состояние одного поручения и связывает исходное и финальное сообщения. **PlanStore** владеет графом, решениями итераций и состоянием задач. **Сервис переходов** координирует изменения turn, checkpoint, задания исполнителю и запись пользовательского события в одной транзакции PostgreSQL. Планер возвращает намерение. Время, идентификаторы, права, смену владельца и запись статусов проверяет runtime.

У одного run бывает много сегментов исполнения. Сегмент начинается начальным запросом или принятым сигналом и заканчивается новой паузой либо терминальным исходом. Один и тот же сегмент после сбоя может получить новую попытку исполнения. Сохранять отдельно стабильный идентификатор сегмента, номер попытки и уникальный токен текущего захвата. Новая попытка получает новый токен. Поздний исполнитель с устаревшим токеном теряет право менять состояние.

Бот отвечает за проверку подлинности событий мессенджера, сопоставление пользователя, адрес обратной доставки и подтверждение доставки. API отвечает за авторизацию и идемпотентный приём. Воркеры отвечают за активные сегменты, диспетчер — за подбор наступивших таймеров и восстановление просроченных захватов. SSE и Redis могут ускорять наблюдение. Состояние восстанавливается из зафиксированных записей.

## 4. Таблица переходов

| До | Событие и условие | Изменения в одной транзакции | После |
| --- | --- | --- | --- |
| Нет run | Первичное упоминание, валидные пользователь и адрес | Создать связь с сообщением, чат, turn, исходный запрос, сегмент и событие принятия | queued |
| queued | Воркер захватил готовый сегмент | Назначить claim, установить lease, записать попытку | running |
| running | TurnPreflight, планер или агент задал вопрос | Сохранить requester, checkpoint и схему ответа, завершить сегмент, записать вопрос для доставки | waiting_input либо waiting_confirmation |
| running | Планер вернул допустимый wait_until | Сохранить checkpoint и wake_at, закрыть сегмент, при необходимости записать обновление для бота | waiting_timer |
| waiting_input | Ответ на активный pause_id прошёл проверку схемы | Сохранить ответ, закрыть паузу, создать единственный следующий сегмент | queued |
| waiting_confirmation | Типизированное решение по действующей паузе | Зафиксировать решение, привязанное к requester и операции, поставить продолжение | queued |
| waiting_timer | Время БД достигло wake_at и совпал активный pause_id | Однократно принять timer_elapsed, закрыть паузу и поставить продолжение | queued |
| running | Сохранён финальный результат | Завершить сегмент и turn, сохранить сообщение и событие доставки | completed |
| running или queued | Неустранимый сбой либо исчерпан бюджет повторов | Закрыть сегмент и run, сохранить диагностический код и безопасное сообщение | failed |
| Любое нетерминальное | Авторизованная отмена победила гонку | Закрыть паузу/задание, инвалидировать claim, применить отмену к плану и зафиксировать исход | cancelled |
| running | Истёк lease | Под блокировкой проверить прогресс и безопасность повтора, передать восстанавливаемый сегмент следующей попытке либо зафиксировать определённый исход ошибки | queued либо failed |

Один run допускает максимум одну открытую паузу и один исполняемый сегмент. У терминального run отсутствуют действующие задания. Для гонки «результат или отмена» победитель определяется под блокировкой, повтор получает фактическое состояние. Для отрицательного ответа сохранить нынешнюю семантику: отказ в операции возвращает управление планеру, false на обычный boolean-вопрос передаётся requester. Отмена всего поручения — отдельная команда.

## 5. Данные и транзакции

1. Расширить статус turn значениями queued и waiting_timer. Добавить режим исполнения для явного выбора между действующим и новым путём на время внедрения. Сохранить неизменные run_id, инициатора, выбранный tenant и время принятия. Время старта очередной попытки хранить отдельно от времени создания поручения.
2. Ввести запись checkpoint уровня run, которая может существовать до появления плана. Минимальные поля — pause_id, run_id, kind, requester, необязательные plan_id/task_id, версия формата, состояние, created_at, resolved_at, wake_at, payload или ссылка на снимок. Для графовой паузы связать её с существующим runtime_pauses по идентификатору. Назначить единственного владельца потребления сигнала. Вторая запись служит привязкой к графу и обновляется той же транзакцией.
3. Ввести таблицу сегментов с run_id, sequence, причиной старта, ссылкой на принятую паузу, статусом, claim_id, lease_until, счётчиком попыток, временем следующей попытки и последней ошибкой. Уникальности на (run_id, sequence) и на сегмент, созданный из конкретной паузы. Индексы для готовой очереди, истёкшего lease и наступившего таймера. Частичные уникальные индексы для активной паузы и открытого сегмента.
4. Хранить привязку поручения к внешнему workspace, беседе, треду и исходному сообщению. Дедупликация входящих команд — по области интеграции и стабильному ID события, с отпечатком значимого содержимого. Повтор возвращает исходный результат. Тот же ID с другим содержимым даёт конфликт. Отдельно связывать опубликованный вопрос с pause_id, поскольку один тред может содержать несколько поручений.
5. Создать очередь исходящих событий в PostgreSQL. Поля — event_id, run_id, sequence, вид, безопасный payload, адресат, состояние доставки, попытки, доступность для повтора и ID сообщения мессенджера при наличии. Последовательность уникальна внутри run. Позволить повторную доставку одного события с тем же event_id.
6. Переходы реализовать в сервисе, который владеет транзакцией. Проработать существующие внутренние commit в SqlPlanStore. Добавить операции с внешним владельцем транзакции для нужных путей, закончить их flush и оставить прежним вызывающим документированную семантику. Принять один порядок блокировок для turn, плана, паузы и сегмента. Репозитории не выполняют commit.
7. Большой снимок сначала загрузить по новому неизменяемому ключу, затем опубликовать ссылку, ревизию и размер при фиксации перехода. До commit продолжает действовать предыдущий checkpoint. Сбой загрузки оставляет операцию повторяемой, потерянные несвязанные объекты удаляются после защитного периода. На чтении проверить версию, владельца и наличие объекта. Сохранить обработку предыдущих форматов checkpoint при деплое новой версии.

## 6. Как работать с состоянием планера

В Pydantic-контракт PlannerStep добавить вариант wait_until и взаимоисключающий payload. Пример полей решения — wake_at с часовым поясом, reason, next_check для описания следующей проверки и необязательный user_update. Структурированная схема для провайдера, локальная валидация и промпт выводятся из одного контракта. Возможность сна явно передаётся планеру для поддерживающего её режима.

Проверять время относительно часов runtime, дедлайна поручения и настроенных пределов. Для «завтра» передавать часовой пояс пользователя и текущее локальное время, хранить абсолютный UTC-момент. Если локальное время существенно и неоднозначно, использовать обычное уточнение. Задать минимальный интервал, максимальный горизонт и лимит пробуждений. Ошибка выбора времени проходит через ограниченный цикл коррекции модели. Просроченный уже сохранённый таймер после простоя обрабатывается однократно с фактическим временем пробуждения.

Обработать два пути в GraphOrchestrator. При первом вызове уже может существовать план без итераций. После выполненных задач предыдущая итерация может держать planner_running. В обоих случаях сохранить идентичность ожидающего вызова планера, корректно передать владение при сне и вернуть его при пробуждении. Сделать явным в PlanStore переход плана в waiting_timer и обратно. Включить его в ограничения БД и в in-memory реализацию. Графовые terminal=planner/synthesis продолжают описывать, кому передать управление после выполнения задач.

Снимок включает цель, TaskBrief, ссылки на исходный запрос и контекст, владельца, идентичность итерации, результаты уже сделанных чтений, сведения для сравнения наблюдений, причину сна, остаток бюджетов и последний опубликованный апдейт. Ссылаться на канонические задачи и результаты. На wake восстановить логическую точку и подать timer_elapsed, planned_wake_at и actual_wake_at. Заново получить текущие дату, доступных агентов, каталог результатов и права на материалы. Старые наблюдения пометить временем проверки. Проверку актуального статуса источника оформить новой задачей с новым task_id.

Проверить TTL результатов и файлов для заявленного горизонта. Если для сравнения достаточно нормализованного статуса и времени наблюдения, хранить их в checkpoint со ссылкой на источник. Если исходный материал истёк или доступ отозван, сообщить планеру об ограничении и решить, разрешено ли новое чтение. Ожидание по календарю исключается из active_wall_time. Суммарные расходы LLM, итераций и попыток переживают все сегменты. Счётчик wake нужен и для сна до создания первой итерации.

## 7. Вход, уточнения и сообщения

Предлагаемый API интеграции использует три команды и поток событий. Реализованные URL и формы запросов перечислены в разделе 13.

| Операция | Контракт |
| --- | --- |
| Принять поручение | Текст, адрес треда, ID события и инициатора, часовой пояс при наличии. После commit вернуть HTTP 202 с chat_id, run_id и идентификатором принятого события. Повтор первоначального упоминания возвращает те же идентификаторы. |
| Ответить на паузу | run_id, pause_id, внешний ID события, типизированное значение. Проверить принадлежность run, автора ответа, активность паузы и схему. Ошибочный тип оставляет паузу открытой. Повтор принятого события возвращает тот же результат, ответ на другую закрытую паузу — конфликт. |
| Отменить | run_id и ID события. Доступ проверяется относительно владельца поручения. Ответ содержит итоговое состояние с учётом гонки с завершением. |
| Получить события и подтвердить доставку | Упорядоченный поток после курсора и возможность дочитать после разрыва. Для выделенного бота использовать подтверждение по event_id; временный сбой мессенджера не переводит успешное выполнение в failed. |

На первом входе передать обычному TurnPreflight признак фонового поручения. Его роль — разрешить ссылки из доступного контекста, уточнить недостающие данные и передать самостоятельный TaskBrief планеру. Если мессенджер ссылается на «эту заявку», адаптер передаёт разрешённый контекст исходного сообщения или ссылку. По ответу на уточнение возобновить исходный preflight с его историей. После planner/agent pause вернуть управление сохранённому requester. Таймер не создаёт пользовательское сообщение и не генерирует question_answer.

События для пользователя — принято, нужен ответ, нужно подтверждение, содержательный апдейт, итог, отмена или ошибка. Первое подтверждение можно собрать из сохранённого состояния без вызова модели. Время следующей проверки показывать после commit таймера. Если планер решил проверить через час без уведомления, обновить статус поручения и расписание без сообщения в тред. Финальный ответ сохранить обычным путём синтеза. В истории различать промежуточное сообщение и финальный assistant_message_id.

Уточнение отправлять боту сразу после надёжной записи. SSE даёт малую задержку, очередь с курсором обеспечивает повторное чтение. При тайм-ауте после отправки во внешний сервис повторить с ключом event_id, если провайдер его поддерживает. Если такой возможности нет, хранить внешний ID и предусмотреть сверку доступными средствами. В этой ситуации доставка сообщения может повториться. Отдельно испытать порядок «вопрос → пользователь ответил → задержанный повтор доставки вопроса».

## 8. Исполнение, восстановление и доступ

- Диспетчер Celery Beat короткими пакетами выбирает наступившие таймеры и готовые сегменты. Использовать время БД и блокировки строк с SKIP LOCKED. Брокеру отправлять стабильный ID. Повторная публикация после рестарта допустима, право исполнения выдаёт БД. Для перегрузки задать размер пакета, параллелизм и интервал подбора через конфигурацию.
- Воркер загружает состояние в новой сессии, повторно проверяет активность пользователя, членство в исходном tenant и доступ к чату. Собрать ToolContext и разрешить текущие права и credentials существующим путём. Снимок не предоставляет новых прав. При отзыве доступа зафиксировать безопасный исход. Подтверждение операции остаётся привязано к пользователю, операции и fingerprint, с действующими правилами подписанного токена.
- Heartbeat продлевает только текущий claim. Любая запись результата, паузы, финала или события проверяет этот claim и ожидаемую ревизию. Проверка нужна на границе фактической записи, включая применение новой итерации. Закрытие HTTP/SSE не отменяет поручение. Команда отмены снимает право на новые действия, пытается остановить текущий вызов и сохраняет сведения об уже совершённых эффектах.
- Повтор активного сегмента восстанавливается из последней зафиксированной точки. Перед выделением новой попытки сверять состояние графа, задач, результатов и guard операций. Если задача уже завершена, продолжать по ledger. Если внешний вызов мог изменить данные и его результат неизвестен, использовать существующую защиту повторной операции и явный исход неопределённости. Повтор всего сегмента с исходного запроса недопустим для такого случая.
- При падении после сохранения ответа, но до выхода в мессенджер восстановить только доставку. При падении после приёма сигнала, но до постановки в брокер сегмент найдёт следующий проход диспетчера. При недоступности S3 или БД применять ограниченные повторы с задержкой и классификацией причины. Потерю обязательного checkpoint показать оператору и завершить предсказуемо.
- Хранить только необходимые сведения треда и привязку к владельцу. Определить, кто уполномочен отвечать в групповом треде и какие данные можно туда публиковать. Для первого релиза принять ответы инициатора и доставлять материалы, разрешённые для этого адресата. Технический токен интеграции сам по себе не определяет полномочия пользователя.

## 9. Изменения для чата, sandbox и эксплуатации

Провести queued и waiting_timer через backend-нормализацию, active-run, reconnect, cancel, статусные снимки, историю и типы клиента. Для ожидания времени показывать следующий момент проверки в часовом поясе пользователя и действие отмены. При ожидании человека показывать вопрос и соответствующие элементы ответа. Проверить открытие чата после нескольких пробуждений и после финала. Сохранить совместимость SSE клиентов при поэтапном включении.

Чат и sandbox уже разделяют часть pause/resume. Сначала включить таймер только для выделенного режима бота, явно передавать runtime доступные возможности, проверить обычный чат и sandbox на регрессии уточнений и подтверждений. Подключать таймер к sandbox отдельным этапом при необходимости. В тестовом окружении обеспечить управляемые часы для проверки дней ожидания за один тестовый прогон.

Связать журналы полями run_id, plan_id, pause_id, segment_id, claim_id и event_id. Метрики — возраст очереди, задержка фактического wake относительно wake_at, истёкшие lease, повторы и отклонённые сигналы, возраст недоставленных событий, число активных и спящих запусков. Дать оператору просмотр причины ожидания, ближайшего wake и последнего подтверждённого события. Отдельно описать ручную повторную доставку сообщения и повтор безопасного сегмента с проверкой ревизии.

## 12. Выкатка, откат и решения перед запуском

Сначала развернуть совместимые читатели и миграцию. Затем включить воркеры и диспетчер с выключенным приёмом новых поручений, проверить heartbeat и подбор тестового задания. Активировать приём для выделенной интеграции. Сравнивать конечные состояния, задержку пробуждения и долю недоставленных событий. Для остановки выката отключить создание новых поручений и оставить исполнителей совместимой версии для уже принятых. Перед удалением схемы или старого формата дождаться завершения, явной отмены либо проверенной миграции всех открытых checkpoint.

Для пилота в eXpress сначала утвердить авторизацию, привязку исполнения и правила публикации в групповые чаты. Зафиксировать ожидаемую точность wake, совокупные бюджеты, сроки хранения событий и правила при истечении источников. Список решений и критерии пилота приведены в разделах 14–15.

При изменении рабочего контракта синхронизировать [архитектуру runtime](docs/architecture/AGENT_RUNTIME.md), [lifecycle чата](docs/architecture/CHAT_TURN_LIFECYCLE.md), [взаимодействия](docs/architecture/RUNTIME_INTERACTIONS.md), ADR маршрутизации и эксплуатационное руководство. Критерий готовности — один логический запуск успешно проходит несколько циклов ожидания с потерей процессов, сохраняет проверяемую историю действий и доставляет пользователю итог в тот тред, из которого поступило поручение.

## 13. Контракт ML Portal ↔ Clouds по коду

### 13.1. Команды и события

Базовый URL внешней системы в Clouds заканчивается на
`/api/v1/integrations/durable-runs`. В текущей версии API использует Bearer,
проверяет владельца запуска и выбирает активный tenant на приёме. Для новых
поручений нужен `DURABLE_RUNTIME_ENABLED=true`. Отключение этого флага закрывает
приём, а ранее принятые поручения могут продолжаться.

| Команда | Запрос | Наблюдаемый результат |
| --- | --- | --- |
| `POST <base>` | `event_id`, `text`, `address`, опционально `timezone` и `referenced_context` | HTTP 202 с `run_id`, `chat_id`, `event_id` и `status`. Повтор того же входного события возвращает прежний run, конфликт содержимого даёт HTTP 409. |
| `POST <base>/{run_id}/responses` | `event_id`, текущий `pause_id`, `value` как строка или JSON boolean | Принимает ответ владельца и ставит продолжение в очередь. Неверный тип даёт HTTP 422, конфликт с текущей паузой — HTTP 409. |
| `POST <base>/{run_id}/cancel` | `event_id` | Возвращает состояние run после попытки отмены. Отказ `false` на подтверждение передаётся requester, команда отмены закрывает поручение целиком. |
| `GET <base>/{run_id}/events?after_sequence=N` | Курсор последнего обработанного события | Возвращает `items` и `next_sequence`. Каждое событие содержит `event_id`, `sequence`, `kind`, `payload`, `created_at`. |
| `GET <base>/{run_id}/event-stream` | `after_sequence` или `Last-Event-ID` | Отдаёт тот же контракт через SSE. ID кадра равен `sequence`. |
| `POST <base>/{run_id}/events/{event_id}/ack` | Опциональный `external_message_id` | HTTP 204. Отмечает доставку события независимо от выполнения run. |

Копатыч использует курсорный GET из отдельного цикла gateway worker. SSE
доступен другим потребителям. `accepted` становится коротким подтверждением
от бота. `waiting_input` и `waiting_confirmation` содержат текст,
`pause_id` и публичную схему ответа. Публикуемый `waiting_timer` содержит
`pause_id`, `wake_at` и сообщение планера. Таймер без пользовательского
апдейта сохраняется в runtime без сообщения в тред. `completed`, `failed`
и `cancelled` закрывают доставку для run. Приватное содержимое checkpoint
остаётся внутри портала.

Контракты кода в [роутере портала](apps/api/src/app/api/v1/routers/durable_runtime.py),
[DTO](apps/api/src/app/schemas/durable_runtime.py) и
[сервисе переходов](apps/api/src/app/services/durable_runtime_service.py).

### 13.2. Привязка в Clouds и возобновление в портале

1. BotX-обработчик принимает исходное сообщение. В группе Копатыч начинает
   поручение по структурированному упоминанию, в личном чате действует
   разрешение gateway. В Portal `integration_id` передаётся как
   `clouds-kopatych`, `workspace_id` равен ID BotX-аккаунта,
   `conversation_id` равен ID чата, `thread_id` и
   `source_message_id` равны sync ID исходного сообщения.
2. Clouds сохраняет связь между `run_id`, исходным сообщением, ботом,
   чатом, автором и внешней системой в `kopatych_runs`. Повтор исходного
   события защищён локальной привязкой и ключом идемпотентности портала.
3. Clouds публикует BotX v4 reply на исходное сообщение. Для ответа на вопрос
   сверяет BotX-аккаунт, чат, автора и sync ID сообщения Копатыча с вопросом.
   В портал уходит `pause_id`. `/cancel` ответом на последнюю публикацию
   поручения или уточнение вызывает отдельную команду отмены.
4. После отправки Clouds сохраняет sync ID и курсор, затем вызывает ACK.
   При повторе недоставленного ACK используется сохранённый ID сообщения.
   Сбой после внешней отправки до сохранения sync ID оставляет риск повторной
   публикации. Метаданные `portal_event_id` позволяют сопоставить события
   при диагностике.
5. Portal хранит очередь, паузы, ревизии и claim в PostgreSQL. Worker
   проверяет активность пользователя и его членство в исходном tenant перед
   сегментом. Human resume возвращается сохранённому requester. Timer wake
   возвращается планеру, минуя новый TurnPreflight. Версионный RunContext
   загружается из MinIO, граф и результаты задач восстанавливаются по тому
   же `plan_id`.

Код адаптера находится в `clouds_bots/src/gateway/kopatych.py`, таблица
вводится миграцией `0007_kopatych_runs`. В ML Portal применяется `0217`.
Кодовые значения по умолчанию для решения планера составляют 60 секунд
минимальной задержки, 30 дней максимального горизонта одного таймера и
100 пауз по времени на run. Они ограничивают механизм ожидания. Предельный
срок конкретного поручения, переданный в тексте, остаётся частью брифа.

## 14. Исходные вопросы по авторизации и привязке исполнения

Первая версия адаптера читала персональный токен по ключу
`<BotX account ID>:<eXpress HUID>` из `GATEWAY_KOPATYCH_USER_TOKENS`.
Внешняя система задаёт URL, а идентичность Portal владельца определяет
предъявленный токен. Адрес треда в запросе и ID пользователя eXpress
описывают связь с мессенджером. Подлинность пользователя портала следует из
Bearer-аутентификации. Наличие записи внешней системы подтверждает
настроенный маршрут, а механизм выдачи прав и привязку аккаунта предстоит
утвердить.

| Решение | Что зафиксировать перед пилотом |
| --- | --- |
| Сопоставление личности | Канонический ключ BotX-аккаунта и HUID, способ однозначной проверки Portal user и tenant, источник истины, создание и отзыв привязки. Отдельно определить поведение при смене eXpress аккаунта или Portal tenant. |
| Полномочия интеграции | Сравнить персональный Bearer с делегированием через удостоверение интеграции и явно подтверждённую привязку пользователя. Определить срок действия, хранение, ротацию и отзыв. Делегирование потребует отдельного контракта API и проверки полномочий на стороне портала. |
| Привязка run и владельца | Определить, какие идентификаторы закрепляются при admit и чем worker подтверждает право работать при wake. Сохранить проверку актуальных прав и tenant, а также однозначную связь действия с первоначальным владельцем. Решить, должен ли отзыв исходного токена останавливать ранее принятый run, приостанавливать его или только закрывать дальнейшие команды и доставку через этот токен. |
| Привязка ответов и адресата | Утвердить, кто вправе отвечать, отменять и получать результат в общем треде. Определить, как изменившийся состав группы или перепривязка бота влияет на позднюю доставку. Развести адрес доставки и полномочия на источники и артефакты. |
| Повтор и смена credentials | Зафиксировать, когда новый токен того же владельца получает доступ к прежнему run, как диагностировать несовпадение владельца и кто устраняет застрявший ACK. Повтор входного события и попытки получить результат должны сохранять исходные ограничения по владельцу и боту. |

UI администрирования сопоставлений, отдельный доверенный способ входа от
интеграции и политика отзыва относятся к этому решению. Текущий способ
через персональные токены задокументирован как реализованный вариант для
разработки. Согласованный вариант для Clouds приведён в разделе 16.

### 15.1. Проверка установки таймеров

Вопрос «установка таймеров не работает» проверен по коду и тестами — дефект
не воспроизведён. Полный путь работает: планер поднимает `TimerPauseRequired`
→ `GraphOrchestrator.pause_timer` пишет `GraphPause` (kind `timer`, status
`waiting`, wake_at в payload) и переводит план в `waiting_timer` → STOP с
reason `WAITING_TIMER` и `timer_context` → durable-ветка `run_paused` →
`DurableExecutionSegment.finish` → `complete_segment` ставит `run`,
`turn`, план и `DurableRuntimePause` в `waiting_timer` одним коммитом →
`accept_due_timers` закрывает паузу и ставит сегмент `timer_elapsed` →
wake-сегмент получает доверительную таймер-континуацию (`pause_id`,
`planned_wake_at`, `actual_wake_at`) и восстанавливает тот же план.

Ключевой инвариант: `DurableRuntimePause.id` равен `GraphPause.id` из
`plan_store.pause_timer`; резервного идентификатора нет, поэтому
`pause_id` в pause-контексте, checkpoint и resume ссылаются на одну запись.
wake-сегмент обязан вызывать планер без повторного TurnPreflight
(fallback-решение строится из сохранённого TaskBrief).

Покрытие тестами:

- [test_durable_runtime_execution_pg.py](apps/api/tests/integration/test_durable_runtime_execution_pg.py)
  — сквозной интеграционный тест на реальном PostgreSQL:
  `claim_next` → `execute_claimed_segment` через настоящий
  ChatStreamService/ChatTurnOrchestrator/RuntimePipeline с `SqlPlanStore`,
  первая пауза (просроченная, сразу due), `accept_due_timers`, второй
  сегмент `timer_elapsed` со второй паузой на 2 часа вперёд. Схема для
  теста клонируется из мигрированной `public` (`LIKE ... INCLUDING ALL` +
  FK из каталога), планер заменён детерминированным `SleepingPlanner`,
  TurnPreflight — фиксированным решением planner-маршрута. Запуск:
  `DURABLE_RUNTIME_PG=1 python -m pytest tests/integration/test_durable_runtime_execution_pg.py`.
- [test_runtime_request_pipeline.py](apps/api/tests/unit/test_runtime_request_pipeline.py)
  — unit-путь: STOP `WAITING_TIMER` с `pause_id` без checkpoint,
  `timer_resume` во втором запросе планера, статусы пауз `elapsed`/`waiting`.
- [test_chat_turn_orchestrator.py](apps/api/tests/unit/test_chat_turn_orchestrator.py)
  — durable-ветка `run_paused`: `finish(waiting_timer)` с pause_id из
  контекста, ассистент-сообщение с апдейтом планера, коммит checkpoint.

Следующий шаг приёмки — сквозная доставка eXpress → Clouds → Portal →
Clouds → eXpress из раздела 15.

### 15.2. Сквозная проверка через эмулятор BotX (2026-11-27)

Полная цепочка проверена локально: эмулятор CTS (BotX) → gateway Копатыч
(pull-режим) → Portal assignments API → durable runtime → события →
BotX-ответы в чат. Подтверждены сценарии: одиночный сон с финалом
(«Время пришло» через 90 секунд), два последовательных сна с user_update
на каждом и финалом («Привет 1» → 65 c → «Привет 2» → 65 c → «Привет 3»),
отмена во сне ответом `/cancel`. Инварианты в реальной цепочке совпали с
интеграционным тестом: `DurableRuntimePause.id == GraphPause.id`, сегменты
`initial`/`timer_elapsed`, пауза `resolved` после wake, доставка
user_update без вопросной семантики.

Проверка вскрыла и закрыла четыре дефекта исполнения (код в WIP):
планер без `kind` (нормализация `infer_kind_from_payload` в
PlannerStep), гонка минимальной задержки с латентностью LLM (границы
`wake_at` меряются от `durable_clock`-якоря через `timer_delay_base`),
отсутствие счётчика пробуждений у модели (`timer_wake_count` в payload,
иначе многошаговые расписания зацикливаются на середине), и слабая
заметность таймерного протокола в промпте (wait_until — собственная
возможность планера, не агент и не инструмент; явно запрещён
`tool_call` с `tool=wait_until`). Медленной модели дополнительно
поднят `request_timeout_s` до 240 секунд. Одиночные ответы до этого
падали из-за исчерпания бюджета LLM-прокси — роли переведены на
`llm.qwen3.27b` (GFN, без лимитов).

Инструмент проверки — эмулятор поддерживает reply-сущности
(`BOTX_EMULATOR_REPLY_TO` в make-цели `botx-send`), что позволяет
тестировать ответы на уточнения и отмену. Dev-окружение: правка
тестовых файлов вешает API из-за `uvicorn --reload`, наблюдающего
весь `/app` (включая `tests/`) — стоит ограничить reload-директорию
исходниками приложения.

Последовательность завершения — настроить выделенный BotX-аккаунт,
секрет коннектора и доступы пилота, затем проверить цепочку eXpress → Clouds → Portal → Clouds → eXpress.
В сквозном тесте сверить оригинальный BotX sync ID, `run_id`, `plan_id`,
`pause_id`, очередь сегментов, курсор и ACK. Отдельно проверить чужого автора
и отзыв доступа в ожидании. Пилот начинается после выполнения этих проверок.

## 16. Согласованный контракт внешних поручений

Для Копатыча реализован отдельный доверенный вход
`/api/v1/integrations/assignments`. Он использует существующую машину
состояний и выдаёт тот же `run_id`. Портал связывает HUID из
аутентифицированного Clouds с LDAP-пользователем и закрепляет его tenant
при приёме. Входной и обратный коннекторы идентифицируются отдельно по
`type:id`. Копатыч сохраняет привязку к исходному BotX-сообщению. Полный
контракт находится в `clouds_bots/ASSIGNMENTS_CONTRACT.md`. Старый
интерфейс с персональным токеном описан в разделе 13.

Решение раздела 14 по первому релизу принято для Clouds. Секрет коннектора
выдаётся при настройке внешней системы, почта подтверждается через CTS
при первой привязке, пользователю нужен предыдущий вход через LDAP и
активный tenant. Для пилота остаётся настроить совпадающий секрет на обоих
сервисах и выполнить сценарии из разделов 11 и 15. Новые типы идентификаторов
включаются после реализации соответствующего доверенного резолвера.

Для исходящего callback портал хранит полный URL приёма событий в
коннекторе типа `integration`. Сервисный Bearer-токен хранится в
существующей вкладке «Креденшалы» этого коннектора. Токен входа
Clouds → Portal по-прежнему настраивается через
`ASSIGNMENT_CONNECTOR_TOKENS`.

Следующий шаг доставки состоит в том, чтобы отправитель сопоставлял
`reply_to` с активным интеграционным коннектором и передавал Clouds
`run_id`, `event_id`, `sequence`, `kind`, `status` и `result`.
Текущая доставка работает через pull API.

Во вкладке «Интеграции» администратор задаёт идентификатор входа, выбирает
исходящий коннектор и выпускает токены для API поручений. Токен можно
отозвать отдельно или отключить интеграцию целиком. Для зарегистрированного
источника действуют выданные в админке токены. Миграция `0220` добавляет
хранение интеграций и токенов.
