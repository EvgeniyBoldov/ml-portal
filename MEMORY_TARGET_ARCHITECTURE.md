# Целевая архитектура Memory

Статус: архитектурное решение

Этот документ описывает целевую модель memory. Существующая реализация и
текущая документация проекта являются `as is` и не считаются источником
истины для этой архитектуры.

## 1. Назначение

Memory — это долговременный семантический слой над документами, RAG и
операционными источниками компании.

Memory должна:

- извлекать из документов устойчивые описания, термины, аббревиатуры, сленг,
  правила и стандартные процедуры;
- помогать системе понимать пользовательский запрос на языке компании;
- автоматически подмешивать релевантное знание в контекст planner и агента;
- позволять агенту быстро использовать проверенное знание без повторного
  чтения одних и тех же регламентов;
- сохранять связь каждого знания с исходными документами и фрагментами;
- возвращать неопределённость и необходимость проверки, если memory
  недостаточно надёжна.

Memory не является заменой RAG, источником текущего состояния систем или
исполнителем операций. Она является компактным, структурированным и быстро
извлекаемым представлением устойчивого знания.

Основное разделение ответственности:

```text
Memory  — понять, вспомнить и выбрать релевантное знание
RAG     — найти и проверить исходные документы и доказательства
Tool    — узнать актуальное состояние внешней системы или выполнить действие
```

## 2. Главный архитектурный принцип

Memory не должна быть пассивным key/value-хранилищем, к которому агент
обращается через низкоуровневую последовательность `lookup/read`.

Для runtime memory является обязательным контекстным слоем между запросом
пользователя и планированием:

```text
Пользовательский запрос
        │
        ▼
Понимание терминов, сущностей и намерения
        │
        ▼
Memory Recall
        │
        ├── релевантная память
        ├── применимые правила и процедуры
        ├── ограничения и неопределённости
        └── решение, нужен ли RAG или tool
        │
        ▼
Planner / Agent context
```

Агент должен получать уже интерпретированный пакет памяти. Он не должен знать
внутреннюю схему хранения, придумывать memory keys или самостоятельно
собирать контекст из множества технических вызовов.

## 3. Типы долговременной памяти

### 3.1. Корпоративный глоссарий

Глоссарий является общим языковым слоем компании. В нём хранятся:

- названия и аббревиатуры;
- внутренний сленг;
- синонимы и варианты написания;
- названия сервисов, платформ и систем;
- короткие определения терминов;
- связи терминов с проектами, продуктами и системами.

Пример семантики:

```text
Термин: Сфера
Тип: внутреннее название сервиса
Означает: сервис управления конфигурациями коммутаторов
Связан с: проектом network-automation
Синонимы: СФЕРА, sphere
```

Глоссарий прежде всего используется для понимания запроса и разрешения
сущностей. Он не должен быть разрозненной копией терминологии каждого
отдела.

### 3.2. Память проекта

Проектная память хранит устойчивые знания о конкретном проекте:

- назначение и границы проекта;
- компоненты и зависимости;
- используемые среды и технологии;
- владельцы и зоны ответственности;
- принятые ограничения;
- связи с сервисами и другими проектами;
- устойчивые решения и рабочие соглашения;
- проектные правила и процедуры.

Проектная память отвечает на вопрос: «как устроена эта конкретная область».

### 3.3. Нормативная память

Правила и ограничения должны быть отдельным типом знания, а не случайным
текстом в поле `value`.

Правило может содержать:

- условие применимости;
- требование или запрет;
- область действия;
- исключения;
- обязательные согласования;
- обязательные проверки;
- consequence при нарушении;
- исходные основания.

Примеры: production-изменение требует согласования, перед изменением
необходимо сохранить конфигурацию, определённые операции запрещены без
подтверждения.

### 3.4. Процедурная память

Стандартные процедуры являются отдельными связными объектами memory.
Например: «как изменить конфигурацию коммутатора в определённом сервисе».

Процедура должна храниться как целое, а не как набор независимых фактов:

```text
Процедура
  Цель
  Условия применимости
  Предварительные проверки
  Последовательность шагов
  Точки подтверждения
  Проверка результата
  Откат
  Исключения
  Источники
```

Это защищает от ситуации, когда retrieval вернул только часть процедуры и
агент построил опасно правдоподобный неполный процесс.

### 3.5. Пользовательский контекст

Пользовательская память содержит только устойчивый персональный контекст:

- роль;
- зона ответственности;
- проекты, с которыми пользователь регулярно работает;
- предпочтения по формату ответа;
- устойчивый технический контекст пользователя.

Пользовательский контекст адаптирует ответ, но не является источником
корпоративных правил или проектных процедур.

## 4. Scope и применимость

В системе должны быть разделены понятия владения, применимости и доступа.
Это не одно и то же.

```text
company
  ├── корпоративный глоссарий
  ├── общие правила
  └── общие процедуры

project
  ├── проектные знания
  ├── проектные правила
  └── проектные процедуры

tenant / отдел
  └── рабочий контекст, задачи и набор доступных проектов

user
  └── персональный устойчивый контекст
```

`tenant` в целевой модели — это отдел или организационная рабочая группа,
а не отдельная компания. Tenant может отличаться от другого tenant:

- набором проектов;
- задачами;
- доступами;
- локальными рабочими соглашениями.

Tenant не должен автоматически владеть копией корпоративного глоссария или
копией проектной памяти. Иначе одинаковые термины и процедуры начнут
расходиться между отделами.

Каждый memory item должен отдельно описывать:

- owner — кто отвечает за знание;
- applicability — где и при каких условиях оно применимо;
- visibility/access — кто может его использовать.

Основные scope: `company`, `project`, `tenant`, `user`. При этом `tenant`
может участвовать в фильтрации и приоритете retrieval, даже если конкретное
знание принадлежит компании или проекту.

## 5. Единица memory

Базовая единица memory — не произвольный key/value fact, а типизированный
`MemoryItem`.

Концептуально он содержит:

```text
MemoryItem
  identity
  type
  meaning / content
  owner
  applicability
  related entities
  confidence
  source evidence
  freshness
  retrieval signals
  state
```

Поддерживаемые типы включают:

- `term` — термин, аббревиатура или сленг;
- `description` — устойчивое описание сущности;
- `relationship` — связь сущностей;
- `rule` — правило;
- `constraint` — ограничение;
- `procedure` — процедура;
- `decision` — устойчивое решение;
- `preference` — пользовательское предпочтение.

Физическая схема может использовать общую таблицу или несколько таблиц, но
семантические контракты типов должны различаться. Процедура, правило и
термин не должны интерпретироваться как один безымянный текстовый факт.

## 6. Извлечение из документов

Обработка документов должна иметь две связанные, но разные ветки:

```text
Документ
  ├── RAG ingestion
  │     └── chunks / embeddings / search evidence
  │
  └── Memory extraction
        ├── термины и aliases
        ├── сущности и связи
        ├── описания
        ├── правила и ограничения
        └── процедуры
```

Memory extraction не должна работать только на случайном chunk. Для правил и
процедур нужно извлекать логическую секцию или группу связанных фрагментов,
чтобы не потерять условия, исключения и шаги.

Пайплайн extraction:

```text
Документ / логическая секция
        │
        ▼
Извлечение кандидатов
        │
        ▼
Нормализация терминов и сущностей
        │
        ▼
Определение scope и applicability
        │
        ▼
Связывание с проектами и системами
        │
        ▼
Проверка дубликатов и конфликтов
        │
        ▼
Публикация в memory
```

LLM может предлагать кандидатов и интерпретацию, но не должен единолично
решать, что неподтверждённая гипотеза стала корпоративной истиной.

## 7. Отсутствие пользовательского версионирования

Полноценное пользовательское версионирование memory на этом этапе не вводится.
Пользователь и агент видят одно актуальное состояние знания.

Однако у memory обязательно должна оставаться provenance-информация:

- из какого документа извлечено знание;
- из каких фрагментов;
- когда источник был обработан;
- когда знание последний раз подтверждалось;
- актуален ли исходный источник;
- есть ли конфликтующие основания.

Это не версия для пользователя, а внутренний механизм доверия, обновления и
отката ошибочного extraction.

Практическая модель:

- один текущий `MemoryItem`;
- набор source bindings;
- `last_verified_at`;
- `freshness` и `state`;
- повторная extraction обновляет item на месте;
- потеря источника переводит item в `stale`, а не удаляет мгновенно;
- противоречие переводит item в `uncertain`;
- memory item без достаточных оснований не используется как уверенное знание.

Таким образом, память может «забывать», ослабевать и сомневаться, не вводя
открытую пользователю систему ревизий.

## 8. Memory Recall

`Memory Recall` — обязательный runtime-компонент, который отвечает за
использование памяти.

На вход он получает:

- исходный пользовательский запрос;
- историю текущего диалога;
- tenant и доступные проекты;
- задачу и профиль агента;
- уже распознанные сущности;
- результаты ранее выполненных операций текущего turn.

Recall выполняет последовательность:

```text
1. Нормализация запроса
2. Разрешение терминов и aliases через company glossary
3. Определение сущностей, проектов, сервисов и среды
4. Определение намерения пользователя
5. Поиск memory items
6. Фильтрация по доступу и applicability
7. Сбор связанных правил и процедур
8. Оценка confidence и freshness
9. Определение, достаточно ли memory
10. Определение необходимости RAG или tool
```

На выход Recall формирует не список ключей, а memory context:

```text
resolved_terms
resolved_entities
relevant_projects
relevant_knowledge
applicable_rules
applicable_procedures
known_constraints
uncertainties
source_references
rag_required
tool_required
```

Агент не должен самостоятельно придумывать ключи memory или знать, в каком
хранилище лежит конкретное знание.

## 9. Гибридный retrieval

Memory Recall должен использовать комбинацию механизмов:

1. Лексический поиск — точные названия, аббревиатуры, коды и варианты
   написания.
2. Семантический поиск — близкие формулировки и описания.
3. Связи сущностей — переходы вида `термин → сервис → проект → процедура`.
4. Фильтрацию по applicability, access и tenant context.

Пример:

```text
«Как поменять VLAN в Сфере?»

Сфера
  → alias корпоративного глоссария
  → сервис управления конфигурацией
  → соответствующий проект
  → процедура изменения VLAN
  → правило согласования изменения
```

Поэтому память должна иметь не только vector index, но и индекс терминов,
сущностей и отношений между ними.

## 10. Взаимодействие с RAG и tools

Memory не должна полностью заменять RAG.

Для каждого recall система определяет один из режимов:

- memory достаточно для ответа;
- memory достаточно для ориентации, но нужна проверка источника;
- memory неполна, требуется RAG;
- memory устарела, требуется RAG;
- memory конфликтует, требуется clarification или проверка источника;
- подходящей memory нет, используется RAG.

Правило использования:

```text
Memory — быстро вспомнить и понять
RAG    — проверить детали и основание
Tool   — получить текущее состояние или выполнить действие
```

Для действий с риском — production changes, security operations,
destructive/write-like operations — процедура из memory должна иметь
достаточную свежесть и при необходимости подтверждаться актуальным RAG
источником или runtime tool.

## 11. Контекст для агента

Агент получает структурированный memory context с разделением:

```text
Понятые термины
Распознанные сущности и проекты
Релевантные знания
Применимые правила
Подходящие процедуры
Ограничения
Неопределённости
Основания
Решение о дополнительном RAG/tool
```

Нужно различать три вида информации:

- `memory statement` — что система помнит;
- `evidence reference` — почему система это помнит;
- `runtime observation` — что прямо сейчас вернул внешний tool.

Эти виды контекста не должны смешиваться в одну неразличимую строку.

Агент может использовать memory для ответа и планирования, но не должен
выдавать memory за текущий факт внешней системы.

## 12. Доверие, обновление и забывание

Memory должна изменяться по сигналам использования и проверки:

- RAG подтвердил memory;
- RAG обнаружил изменение;
- memory оказалась недостаточной;
- memory оказалась нерелевантной;
- пользователь исправил термин или правило;
- процедура была применена успешно;
- процедура оказалась неполной или неприменимой.

Эти сигналы могут влиять на confidence, freshness, retrieval priority и
необходимость повторной extraction.

Ответ агента сам по себе не является доказательством. Нельзя сохранять его
как новое знание только потому, что он звучит убедительно.

## 13. Безопасность и границы

В memory запрещено сохранять:

- пароли, токены, ключи и credential material;
- stack traces и технические ошибки провайдеров;
- raw payloads и необработанные журналы;
- внутренние runtime IDs, если они не являются бизнес-сущностями;
- неподтверждённые гипотезы;
- временные намерения пользователя;
- случайные детали текущего диалога.

Memory не получает произвольный доступ к базе данных. Все чтение и запись
проходят через memory subsystem с проверкой scope, access и evidence.

## 14. Целевая схема компонентов

```text
                         ┌─────────────────────┐
                         │ Documents / Sources │
                         └──────────┬──────────┘
                                    │
                  ┌─────────────────┴─────────────────┐
                  ▼                                   ▼
          ┌───────────────┐                   ┌───────────────┐
          │ RAG ingestion │                   │ Memory        │
          │ chunks/index  │                   │ extraction    │
          └───────┬───────┘                   └───────┬───────┘
                  │                                   │
                  ▼                                   ▼
          ┌───────────────┐                   ┌───────────────┐
          │ RAG evidence  │                   │ Semantic      │
          │ and retrieval │                   │ memory        │
          └───────┬───────┘                   └───────┬───────┘
                  │                                   │
                  └─────────────────┬─────────────────┘
                                    ▼
                           ┌────────────────┐
                           │ Memory Recall  │
                           │ understand     │
                           │ retrieve       │
                           │ assess         │
                           └───────┬────────┘
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
                 Planner         Agent           RAG/tool
```

## 15. Критерии готовности целевой архитектуры

Архитектура считается реализованной концептуально, когда:

- новый термин из документа автоматически становится доступен для понимания
  пользовательского запроса после подтверждённого extraction;
- запрос с аббревиатурой разрешается через company glossary;
- вопрос о проекте автоматически находит проектную память без ручного
  перебора ключей;
- стандартная процедура возвращается целиком, включая условия, проверки и
  откат;
- memory используется до планирования, а не только после явного tool call;
- агент получает применимые правила и ограничения автоматически;
- система умеет сказать, что памяти недостаточно или нужна проверка RAG;
- у каждого важного знания есть provenance;
- tenant влияет на доступность и приоритет проектов, но не создаёт лишние
  копии корпоративного знания;
- ответ агента не может сам по себе превратиться в durable memory;
- устаревшее или конфликтное знание не используется как безусловная истина.

Эта схема является направлением развития memory: сначала формируется
семантическая модель и Recall-контур, затем под неё адаптируются хранение,
extraction и runtime-интеграция.
