# План реализации Memory UI

Этот документ фиксирует верхнеуровневый порядок реализации UI поверх целевой архитектуры в [MEMORY_TARGET_ARCHITECTURE.md](MEMORY_TARGET_ARCHITECTURE.md). Детальные технические задачи и остаток production rollout ведутся в [TODO.md](TODO.md).

## Фаза 1. Пользовательские виртуальные коллекции

- Показывать Glossary и Project Memory в общем каталоге коллекций как специальные read-only представления, не создавая записей в таблице `collections`.
- Сначала завершить backend read-модели: поиск, фильтры, состояния, freshness, applicability, entity/project links и tenant-safe evidence.
- Glossary представить как каталог терминов, aliases, определений и связанных сущностей.
- Project Memory представить как набор типизированных знаний проекта: descriptions, relationships, rules, constraints, procedures и decisions.
- Процедуры отображать целиком: цель, условия, approvals, prechecks, steps, verification, rollback и exceptions.
- В загрузке документов показывать effective memory policy и разрешить выбрать проекты из общего корпоративного каталога.
- Не разрешать пользователю вручную редактировать semantic content.
- Опциональный будущий режим «Попробовать запрос» проектировать как read-only проверку Recall, без записи в память.

**Критерий завершения:** пользователь может найти и понять доступное ему знание и открыть его evidence, не видя claims других tenant.

## Фаза 2. Conversational extraction в Sandbox trace

- В trace показывать только extraction из пользовательского диалога и runtime evidence: персональные предпочтения, устойчивый пользовательский контекст и допустимые tenant facts.
- Не показывать document semantic extraction в Sandbox: он принадлежит RAG ingestion и административной диагностике.
- Разделить trace на кандидатов, решения compactor/reconciler и фактически опубликованные изменения.
- Для каждого результата показывать scope, evidence, решение accepted/rejected/conflict и безопасную причину.
- Не показывать raw prompts, credentials, закрытые payloads и внутренние технические данные.
- Переименовать устаревшие UI-термины, которые создают впечатление, что Sandbox управляет Project Memory.

**Критерий завершения:** по trace понятно, что система запомнила из разговора и почему, при этом документная память там не дублируется.

## Фаза 3. Административный раздел «Мемори»

- Добавить пункт «Мемори» в основной admin navbar.
- Главную страницу построить как обзор здоровья памяти: количество active/uncertain/stale, ошибки extraction, конфликты и источники, требующие внимания.
- Добавить представления:
  - каталог semantic memory с поиском и фильтрами;
  - Glossary и Project Memory в административной проекции;
  - карточка MemoryItem;
  - сравнение claims;
  - цепочка документ → section → claim → MemoryItem → relations → использование;
  - список документов и состояние memory extraction.
- Разрешить управление через источники и lifecycle: включение документа, re-extraction, исключение источника, повторную проверку и разрешение конфликта.
- Не добавлять свободное inline-редактирование semantic content; исправление знания проходит через документ, evidence и повторную extraction.
- Добавить polling задач, понятные ошибки и переход к исходному документу.

**Критерий завершения:** администратор может объяснить происхождение любого знания, диагностировать конфликт и безопасно инициировать его пересборку.

## Общие проверки и порядок

- Фазы реализуются строго последовательно: виртуальные коллекции → Sandbox trace → admin Memory.
- Для каждой фазы обязательны frontend typecheck/build, component tests, accessibility и responsive-проверка.
- ACL проверяется отдельными сценариями для global и двух tenant: content, aliases, counters и evidence не должны утекать.
- После третьей фазы выполнить controlled re-extraction и smoke-проверку на реальных документах.
- Документ содержит только верхнеуровневый порядок; технические подзадачи и остаток production rollout ведутся в [TODO.md](TODO.md).
