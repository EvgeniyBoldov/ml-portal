# Предложение по структуре инспекторов планера и агента

Дата: 08.11.2026. Статус: предложение для обсуждения; код и действующие контракты не изменены.

Основание: [визуальный отчёт дизайнера](SANDBOX_EXECUTOR_INSPECTOR_REVIEW_2026-11-08.md), текущие frontend-проекции, runtime-модели и документы `SANDBOX_RUNTIME.md`, `RUNTIME_TRACE_SPEC.md`, `AGENT_RUNTIME.md`. Дизайнер проверил живую песочницу; архитектурная часть сверяет эти наблюдения с кодом.

## Архитектурный выбор

Убрать отдельный таб «Инфо» у планера и обычного агента. Сейчас он состоит из статуса и ресурсов; самостоятельного содержания у него нет. Перенести эти сведения в общую шапку инспектора и раскрываемый блок «Ресурсы выполнения» под ней.

Основное содержание распределить так:

| Исполнитель | Таб | Единственный вопрос, на который он отвечает |
| --- | --- | --- |
| Планер | План | Какое решение принято и какие задачи назначены? |
| Планер | Вход | С каким запросом, уточнениями и ограничениями планер начал работу? |
| Агент | Задача | Что поручили этому исполнителю? |
| Агент | Результат | Что он вернул, чего не хватило и что произошло дальше? |

«Доступ», «Лимиты», «Операции», «Память», «Промпт» сохраняют свои области ответственности и показываются при наличии соответствующих снимков. RAW остаётся последним диагностическим табом. Новый таб для технических receipts не нужен.

Для завершённого планера при первом выборе открывать «План», для завершённого агента — «Результат»; у работающего агента — «Задача». После выбора пользователя таб не переключать автоматически при поступлении новых событий.

## Что подтверждено кодом

1. `ExecutorInfoViewer` показывает только статус, длительность и `statistics`. Сходные сведения уже есть в карточках timeline. `TaskViewer` дополнительно выводит статус задачи, `ExecutorResultFields` — ещё один статус. Три представления не используют единый компонент состояния.
2. В моделях есть разные понятия: lifecycle запуска, состояние логической задачи, agent-owned `completion`, orchestration `outcome`, достаточность для этапа. Одинаковый текст «Готово» скрывает различие между ними. Состояние задачи может охватывать несколько попыток; состояние выбранного запуска относится к одной попытке.
3. Результат протокола v2 допускает `answer: null` при содержательном `structured_response`. Это допустимый ответ, а не самостоятельная ошибка.
4. `TaskResult` хранит одновременно пользовательские данные, compatibility `outputs`, runtime `verified`, `diagnostics`, `output_states`, attachments и sources. Весь этот объект не должен становиться содержимым поля «Результат».
5. Есть конкретное расхождение с действующим описанием `RUNTIME_TRACE_SPEC.md`: в `executorResultFor()` переменная `final` заполняется только у synthesizer. У обычного агента ветка `parsedFinal`/`declaration` поэтому не получает owned `final`. `resultOutputFrom()` выбирает целиком `result`, если он есть, и семантический таб получает оболочку `TaskResult`. Это объясняет наблюдаемый дамп протокола и требует исправления проекции, а не добавления фильтров в React Viewer.
6. Вход планера берётся из снимка `context_snapshot.inputs` владельца-orchestrator. Это нормализованный исходный запрос и `task_brief`; это не точная копия динамического входа каждого planner LLM-вызова. Execution ledger и фактический каталог доступных агентов остаются во вкладке запроса конкретного LLM-вызова.
7. Существующая документация требует сохранять явно переданный пустой agent input `{}`. Его можно компактно представить как «Дополнительных параметров нет», но нельзя слить с состоянием «Входные данные не записаны».

## Общая шапка и ресурсы

В шапке: читаемое имя исполнителя, тип «Планер»/«Агент», короткое описание роли из записанного снимка, один статус выбранной попытки, длительность. Короткое описание роли показывать при наличии в журнале; текущую конфигурацию из каталога не выдавать за конфигурацию исторического запуска.

Статус должен иметь единый enum, локализованный label и tone, подготовленные общей проекцией. Timeline и инспектор используют одно представление состояния выбранного запуска. Техническая ошибка, отмена или незавершённое выполнение имеют приоритет над заявлением модели об успехе. `unfulfillable` не окрашивается как успешный результат, даже если coroutine закончилась нормально.

Внутри «Задачи», «Входа», «Плана» и «Результата» повторное поле «Статус» не выводить. Если в плане перечислено несколько логических задач, у каждой остаётся собственный явно подписанный статус: он относится к другой сущности и полезен для сравнения. Он не должен выглядеть как повтор статуса запуска планера.

«Ресурсы выполнения» раскрываются в одном месте под шапкой: LLM-вызовы, вызовы инструментов, токены с разделением вход/выход/всего, повторы и ошибки. Счётчики не дублируются в содержимом табов. Лимиты и остатки показываются только в «Лимитах»; сейчас `StatisticValue` дополнительно прикрепляет квоты к статистике «Инфо», что пересекает области ответственности.

Фраза «Задача запланирована» или «Получено 50 устройств» относится к содержательному решению/ответу и должна находиться в «Плане»/«Результате». Шапка не должна генерировать вторую независимую сводку.

## Планер: «План»

Порядок блоков:

1. **Решение.** Применённый план, отклонённый план или ошибка планирования. Разделять валидное предложение и фактически применённый план; нормальный ответ LLM сам по себе не доказывает применение. Для `terminal=planner`: «После задач — повторная оценка»; для `terminal=synthesis`: «После задач — подготовка ответа». Не показывать raw `Terminal`.
2. **Основание решения.** Локализованный recorded trigger («Первичное планирование», «Повторное планирование…») и записанная причина. Это не цепочка рассуждений LLM. Если подробной причины нет, не сочинять её из содержимого задач.
3. **Назначенные задачи.** Вертикальные карточки: цель, читаемое имя агента, необходимые действия, зависимости по названиям, критерий/запрошенный вид результата. В 320 px не использовать многоколоночную таблицу задач. Task ID нужен для связи и RAW, в основном виде скрыт.
4. **Исполнение и продолжение.** Ссылки из задач на фактические попытки агента; после них — связанный checkpoint и следующее действие, только когда они записаны. Отдельно подписать «После выполнения» — это последующая история, а не часть решения, известная планеру заранее.

Название/цель/intent/инструкции не следует объединять LLM-суммаризатором ради интерфейса. Проекция выбирает цель в документированном порядке; точные повторяющиеся строки выводятся один раз. `intent` показывается только если он добавляет смысл, с названием «Тип работы». Длинные инструкции раскрываются под «Подробности задачи».

`response_spec.mode` — запрошенный формат («Текст», «Структурированные данные», «Файл»), а не доказательство полноты. Схема рекомендательна по действующему runtime-контракту. Нельзя переименовать её в обязательный «Критерий успеха», если настоящего критерия в данных нет. Формат можно компактно показать в подробностях; настоящий критерий — отдельным текстом, если он записан.

План без задач допустим, если далее предусмотрен синтез. Вместо тревожного пустого блока «План не содержит задач» показывать записанное продолжение: «Подготовить ответ по имеющимся данным».

## Планер: «Вход»

Название «Вход» оставить, внутри использовать заголовок «Исходные данные планирования». Убрать JSON-обёртку «Вход planner» и отрисовать типизированные части:

| Блок | Источник | Правило |
| --- | --- | --- |
| Запрос пользователя | recorded `inputs.goal` | Основной текст; не повторять его как ещё одну цель в «Плане» |
| Уточнённая задача | `task_brief.goal`, `direction`, `expected_result` | Не повторять строки, совпадающие с запросом; поля имеют понятные русские названия |
| Ограничения | `task_brief.constraints` | Список; пустой скрыт |
| Уточнённые ссылки и объекты | `resolved_references`, `entity_hints` | Читаемые значения; непрозрачные ссылки разрешаются только по записанным данным |
| Что осталось неясным | `uncertainties` | Список, только если записан |
| Выбранные материалы | доступные recorded reference labels | Короткие ссылки; это не содержимое «Памяти» и не каталог «Доступа» |

Не добавлять сюда prompt, доступных агентов, metrics и сформированные задачи. Динамический ledger повторного планирования не выдавать за часть сохранённого исходного input: точные сообщения доступны у конкретного LLM-вызова. Если продукту нужен отдельный обзор «Что учтено при этом повторном решении», runtime должен записать per-iteration snapshot (см. ниже).

**Отдельное расхождение, обнаруженное дизайнером в «Входе».** В `task_brief.constraints` перечислены как доступные `memory.search`, `file.read`, `chat.history.read`, но план назначает `inventory.netbox`. Сейчас `constraints` — список текстовых ограничений задачи, а фактический каталог агентов и инструментов разрешается другими механизмами. По этому экрану нельзя доказать ни нарушение доступа, ни корректность такого brief. До реализации нужно сопоставить записанный brief, точный planner LLM request (`available_agents`/инструкции), access snapshot и реально разрешённые операции NetBox. Проверить, не перенёс ли preflight список собственных тулзов в ограничение всей задачи. Если это так, исправлять генерацию brief/промпт в runtime; не скрывать противоречие переименованием в интерфейсе. Строки `constraints` нельзя использовать как источник истины для статуса доступа. Само это наблюдение не является доказательством обхода RBAC.

## Агент: «Задача»

Последовательность: цель → действия/инструкции → непустые параметры → данные от других задач → ограничения/запрошенный результат.

- Использовать фактически назначенную задачу из owned start/context snapshot с сохранением plan provenance, а не подменять её последней версией плана.
- Название и цель не выводить двумя одинаковыми абзацами. Читаемое назначение — в цели; технический intent скрыть, если он ничего не добавляет.
- Состояние попытки сюда не включать. Состояние логической задачи при нескольких попытках показывать рядом со ссылками на попытки, только если это отдельный пользовательский вопрос.
- Объект входов представлять компактной таблицей параметров или bounded structured viewer. Явный `{}` — короткое «Дополнительных параметров нет»; отсутствие снимка — «Входные данные не записаны». Нулевые значения, `false`, `null`, пустые списки внутри предметных данных сохранять.
- Зависимости называть по задачам и связывать с их результатами. UUID/slug задачи не служит основным текстом.
- Запрошенный формат держать отдельно от настоящего критерия результата. Не показывать «схема рекомендательная» крупным блоком в основном чтении задачи.

## Агент: «Результат»

Порядок блоков:

1. **Ответ.** Непустой `answer` или безопасная записанная summary. При `answer:null` блок просто отсутствует; не выводить пояснение о техническом nullable поле. Если присутствуют и текст, и структурированные данные, сохранить оба.
2. **Данные.** `structured_response`; для legacy — адаптированное содержимое `outputs` без runtime-оболочки. Если compatibility `outputs` повторяет `structured_response`, показывать одно каноническое представление. Предметное поле с именем `outputs` внутри произвольного ответа нельзя удалять по одному совпадению ключа.
3. **Ограничения и продолжение.** Записанные needs, limitation, reason_code и безопасное пояснение ошибки/остановки. `completion=needs` — «Для продолжения требуется…»; `unfulfillable` — записанная причина; `fulfilled` — заявленное исполнителем выполнение поручения. Это не универсальная автоматическая проверка правильности данных.
4. **Материалы.** Валидные runtime-файлы/attachments и явно зарегистрированные sources/citations с читаемыми названиями. Не показывать пустые секции.
5. **Ход работы.** При наличии полезных ссылок — используемые вызовы/результаты, а затем записанное решение orchestration «принято / назначено продолжение / ожидание» со ссылкой на checkpoint. Это отдельный факт последующей оценки, не новый статус результата агента.

Данные рендерить общим typed viewer: текст, скаляр, список значений, таблица однородных записей, группы полей объекта; ограниченный preview и расширение для больших данных. Не писать отдельный NetBox renderer и не вшивать `devices`, `total_devices`, `completeness` в универсальную проекцию агента. Известные доменные схемы могут дать labels/компонент, но отсутствие схемы не запрещает показать фактические данные.

Полноту разделять на независимые смыслы: что получил агент, что сохранено в trace, что охвачено в источнике и что агент считает выполненным. `sufficient_for_phase` — отдельная записанная оценка этапа, а не аналог глобального «Готово». Отсутствующее значение не заменять `true`. Процент в произвольном structured response не объявлять runtime-проверенной полнотой и не вычислять свой процент из случайно похожих полей.

В частности, в дизайнерском примере «50 из 72» и «72%» нельзя использовать как готовый эталон вычисления: 50/72 не равно 72%. Следует сохранить исходные значения в их предметном контексте; если нужен общий показатель покрытия — согласовать типизированный контракт и его происхождение.

Receipts/хэши/evidence IDs остаются в RAW. Для смысловой навигации проекция может дать ссылки на вызовы с именем операции и источника. `sources: []` при наличии tool receipts не противоречие: citations и журнал выполненных операций отвечают на разные вопросы. Не превращать успешный tool call автоматически в подтверждение правильности конкретного вывода.

## Что решается фронтендом, а что требует runtime

| Изменение | Владелец и граница |
| --- | --- |
| Единая шапка, статусы, ресурсы, удаление «Инфо», политика табов | Frontend: общая typed projection + shared viewers; обновить owning sandbox presentation contract |
| Правильный выбор owned final, разбор TaskResult/v2, legacy adapter, отсутствие повторного envelope | Frontend projection: исправление расхождения с существующим контрактом; Viewer не сканирует события |
| Читаемый «Вход», компактный явный пустой input, labels trigger/terminal/response mode | Frontend: типизированные модели из уже записанных полей; неизвестные поля только RAW |
| Связь план → задачи → попытки → checkpoint | Frontend: использовать существующие IDs/parent links; при отсутствии явной связи показывать только известную часть, не угадывать по времени |
| Более понятные имена/описания исторического агента | Runtime metadata snapshot там, где label/description не записаны; не читать текущую конфигурацию как историю |
| Причина выбора конкретного агента, критерий достаточности, объяснение перепланирования | Только записанные runtime/LLM-поля. Если их нет — optional контракт с явным владельцем; не генерировать задним числом |
| Контекст конкретной повторной итерации | Если нужен в semantic input: optional `planner_iteration_start` snapshot нормализованных входов/trigger/recorded ledger summary. Исходный orchestrator input не становится per-iteration snapshot |
| Универсальная человекочитаемая сводка arbitrary structured data | Не требовать нового LLM-вызова для инспектора. Текст — из существующего answer/summary; structured viewer показывает факты. Отдельное поле summary можно добавить позже, если нужен продуктовый контракт |

Не добавлять второй event stream, backend presentation schema, дублирующую Pydantic task protocol, или отдельный API для вычисления истории из живой конфигурации. Старые журналы продолжают читать existing legacy adapter; новые optional snapshots обогащают только новые запуски.

## Порядок реализации и проверки

1. Зафиксировать структуру табов, единый статус и canonical result model в `SANDBOX_RUNTIME.md`/`RUNTIME_TRACE_SPEC.md`. Не менять смысл runtime completion ради интерфейса.
2. Сначала исправить shared result projection с воспроизводимыми journal fixtures для v2, legacy и lifecycle-only `agent_end`. Это убирает основной шум в Sandbox и admin одновременно.
3. Затем переделать шапку/ресурсы, «Задачу» и «Вход», убрать «Инфо» и дубли из tab Viewers. Перевести plan tasks и continuation на типизированную модель со ссылками.
4. Добавить runtime snapshot только для подтверждённых пробелов (per-iteration context/labels/reason), отдельно согласовав optional контракт. Не блокировать очистку существующего интерфейса полями, которых ещё нет.
5. Отдельно проверить происхождение ограничения списка тулзов в `task_brief.constraints` и его согласованность с назначением `inventory.netbox`; по результату исправить brief или его точную семантику. Проверку не подменять изменением отображения.
6. Пройти Chromium на том же trace, затем на новых запусках с ошибкой, needs, повторным планированием и отказом доступа. Снять planner/agent в 320 px инспекторе; открытые строки/длинные тексты не должны растягивать колонку.

Минимальные регрессии:

- V2 `answer:null` + непустой `structured_response`; текст + structured одновременно; values `0`, `false`, `null`, `{}`, `[]` не теряются.
- Legacy `outputs` + дублирующий structured response; protocol metadata остаётся RAW, предметные одноимённые поля сохраняются.
- Lifecycle-only `agent_end` + принадлежащий тому же агенту final; соседний чужой final не присваивается; intermediate LLM response не становится итогом.
- Модель заявила fulfilled, но lifecycle failed/cancelled; частичные данные сохраняются, общий статус не становится зелёным.
- Needs/interaction/unfulfillable; отсутствие достаточности не интерпретируется как успех/неуспех полноты.
