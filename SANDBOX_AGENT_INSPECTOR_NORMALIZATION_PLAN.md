# План нормализации инспектора агента

Основание: личный Chromium-осмотр `inventory.netbox` в sandbox `2ee9f5cc-c3b0-4db4-a247-05e9064e05e3`, описанный в `SANDBOX_AGENT_INSPECTOR_SELF_REVIEW_2026-11-08.md`.
Статус: реализация и личная проверка root в Chromium завершены. Навигация скорректирована по последующему пожеланию пользователя: прежние вкладки восстановлены.

## Цель

Инспектор должен последовательно отвечать на вопросы: что поручили, что получилось, какие данные и возможности были доступны, сколько ресурсов использовано. Технический формат остаётся доступным по явному выбору. Основные сведения читаются непосредственно в панели.

## 1. Общая оболочка

- Сделать ширину панели регулируемой перетаскиванием разделителя. На desktop целевая начальная ширина 400–420 px при достаточной ширине окна; на имеющихся 320 px все основные компоненты тоже должны работать. Сохранять выбранную ширину локально.
- Шапка: читаемое имя агента, короткое описание роли при наличии в snapshot, единый статус и длительность. Исключить дубли содержимого вкладок и метрик расхода.
- Сохранить прежнюю общую навигацию `InspectorTabs`, как у планера. Агент открывается на «Задача», «Результат» добавляется по наличию записанного результата. Выбранная вкладка сохраняется при новых trace-событиях той же сущности; открытые модальные viewers закрываются при смене вкладки. Ширина панели регулируется внешним keyboard-accessible separator.
- Основной текст 13–14 px, обычный шрифт. Приглушённые подписи; моноширинный шрифт только для кода, JSON и технических имён. Ограничить количество вложенных рамок.

## 2. Общие компоненты

| Компонент | Поведение |
| --- | --- |
| Section | Заголовок, необязательный счётчик, основное содержимое. Один стиль отступов и вторичного текста |
| FieldViewer | Название и читаемое значение; многострочный текст на всю ширину; короткое значение в компактной строке |
| Details | «Подробнее», «Примечания», «Показать ещё N» с указанием содержимого. Раскрытие сохраняет исходный текст и положение чтения |
| DataViewer | Просмотр данных как полей, таблиц и групп. В полном просмотре переключатели «Представление / JSON»; JSON служит техническим режимом |
| AdaptiveTable | Число колонок зависит от задачи. Основные значения помещаются в панели; дополнительные поля раскрываются у строки |
| StateNotice | Понятное ограничение или запрос на продолжение с кратким действием. Цвет используется для смысла состояния |
| FullView | Понятный заголовок выбранного поля; тот же способ представления, что в панели, плюс явный технический режим при необходимости |

Длинный текст раскрывается на месте; отдельное окно нужно для больших таблиц/документов. Короткие строки не получают кнопку огромного Viewer. Пустые контрактные секции скрываются; фактически возвращённые `0`, `false`, `null`, `{}` и `[]` сохраняются. Отсутствие записи отличается от пустого значения.

## 3. Задача

- Цель — обычный текст достаточного размера на всю ширину, без серого редактора. Основное поручение открыто сразу.
- Дополняющие инструкции — отдельный блок; точные дубли цели не повторять. Длинные инструкции раскрываются на месте.
- Непустые параметры — FieldViewer/DataViewer; факт явно переданного пустого объекта можно коротко указать вторичной строкой.
- Ожидаемый результат — записанное описание ожидаемых данных. Формат ответа — компактная вторичная подпись. Не приравнивать формат к критерию успешности.
- Полный просмотр называется «Задача агента» или названием конкретного поля.

## 4. Результат

### Последовательность

1. Запрос на продолжение/ограничение, требующее действий, — заметный блок, если такой исход записан.
2. Текстовый ответ, если он есть.
3. Основные структурированные данные.
4. Файлы и источники.
5. Дополнительные примечания, ход получения результата, замечания к формату.

### Данные

- Короткие значения — компактные строки с различимыми подписями и значениями; короткие числовые показатели не конкурируют с длинными пояснениями.
- Массив простых записей — таблица с выравниванием чисел, читаемыми заголовками, числом строк и раскрытием остатка.
- Сложные записи — группы полей; глубокие уровни раскрываются отдельно.
- Длинные текстовые поля — на всю ширину, в дополнительных подробностях. Их содержание остаётся в structured_response.
- Полный просмотр открывает увеличенное читаемое представление. Переключение в JSON сохраняет исходные ключи и значения.
- Подписи и порядок брать из записанной схемы при наличии; иначе использовать универсальные правила по типам. Не строить продуктовую структуру на жёстко заданных ключах NetBox.
- Не вычислять и не выдавать за проверенные KPI произвольные проценты или полноту из ответа модели. Противоречивые значения не исправлять молча.

### Остальные сущности

- Needs: карточка описания, метка типа данных/файла/решения, обязательность. Технические ref/key остаются в RAW.
- Файлы: тип, имя, описание, размер, доступные действия просмотра/скачивания через действующий API.
- Источники: читаемое название и вторичная подпись домена/сервиса; подтверждённая безопасная ссылка.
- Выполненные действия инструмента доступны в трейсе и не дублируются в результате агента.
- Diagnostics: сгруппированные предупреждения о формате с количеством и понятными деталями. Не превращать обычное notes в диагностику.
- Пустые блоки не занимают места. Фактические tool receipts не превращаются автоматически в citations или доказательство правильности ответа.

## 5. Память

- Начинать с пояснения «Контекст, доступный агенту при выполнении задачи» обычным вторичным текстом. Убрать редактор и раскрытие этой подписи.
- Группы: факты пользователя, контекст задачи и другие реально записанные области. Для каждой — количество и читаемые поля.
- Известные системные свойства получают понятные подписи; оригинальный ключ доступен в подробностях. Произвольные имена пользователя сохраняются.
- Верхнюю карточку «Контекст подготовлен» с суммарными счётчиками убрать; счётчики групп и факты сохраняются.
- Полный просмотр открывает факты выбранной группы, а не одну поясняющую фразу. Длинные группы раскрываются.

## 6. Доступ

- В таблицах агентов/источников показывать только применимые колонки. Пустую колонку «Источник» у самих источников убрать.
- Для тулзов основной вид: название и статус; бейдж источника под названием. Описание — на следующей строке либо в раскрываемых деталях записи. Это даёт инструменту достаточно ширины.
- Источник блокировки и причина остаются связаны со статусом. Доступность показывается отдельно от декоративного цвета сервиса.
- Длинные названия переносятся по смысловым разделителям, а не по произвольным буквам. Копирование точного имени доступно из подробностей.
- Если descriptions отсутствуют в историческом snapshot, не создавать колонку из одних прочерков и не подменять историю текущим каталогом.

## 7. Лимиты и расход

- Единая таблица из трёх основных колонок: «Параметр / Расход / Лимит». Она целиком помещается в панели.
- Расход, лимит и остаток/перерасход видны прямо в строке. Usage bar показывается только если recorded расход известен и лимит положительный; отдельная цветная метка остаётся у предупреждений и превышений. При отсутствующем расходе/лимите показывать «не записан», не вычислять фиктивный процент. Пояснение учтённого времени не отображается.
- Один параметр — одна строка; токены входа, выхода и всего сохраняют разные явно подписанные значения. Не дублировать тот же total из двух источников.
- Числа форматируются единообразно; единицы времени указываются явно.
- Отсутствующий лимит не выдавать за исчерпанный. «Не записан», «Не задан» и явное отсутствие ограничения различать по имеющимся данным.
- Не показывать поясняющую подпись/раскрытие учтённого времени. Нормальный расход показывать шкалой без отдельного бейджа «В норме»; предупреждения и перерасход обозначать явно.
- Горизонтальная прокрутка для этой таблицы не нужна.

## 8. Промпт

- Просмотр документа с понятными разделами, переносами и поиском; исходный текст доступен через явный режим «Исходный текст».
- Для Markdown-промпта использовать существующий безопасный viewer, разделы по заголовкам, сворачиваемые длинные служебные части. Произвольный текст результата не объявлять Markdown по догадке.
- Основные Identity/Mission/Scope открыты; длинные каталоги и протоколы можно свернуть под подписанными заголовками.
- Полное окно называется «Промпт агента»; оно сохраняет режим просмотра. Убрать бессодержательный заголовок Viewer.

## 9. RAW

- Список событий с порядковым номером и типом; payload по умолчанию свёрнут.
- При раскрытии — единый JSON viewer с деревом, поиском и копированием; отдельное полное окно события.
- Не использовать по маленькой textarea с собственными двумя скроллами на каждую запись.
- Технические идентификаторы и исходные ключи сохраняются здесь.

## Порядок реализации

1. Общая оболочка, навигация, FieldViewer/Details/FullView. Сначала убрать разные варианты просмотра одной и той же строки.
2. Лимиты и доступ: устранить доказанные проблемы ширины и доступности колонок.
3. Результат: DataViewer и сущности needs/files/sources/diagnostics, читаемый полный просмотр.
4. Задача и память: применить общие поля, убрать бессодержательные раскрытия.
5. Промпт и RAW: использовать документный и JSON viewer, нормализовать навигацию по длинным данным.
6. Общий Chromium-проход, focused проверки и актуализация owning docs. Каждую итерацию проверять визуально до перехода к следующей.

## Критерии приёмки

- На ширине 320 px доступны название параметра, расход и лимит одновременно; на 420 px интерфейс использует дополнительное место.
- Навигация соответствует исходному `InspectorTabs` планера, включая прежнюю горизонтальную прокрутку вкладок; содержание разделов нормализовано.
- У каждого раскрытия понятное название, реальное дополнительное содержимое, работа с клавиатуры и предсказуемое закрытие.
- Полный просмотр сохраняет читаемое представление; JSON включается явно.
- Основные данные видны сразу, длинные технические подробности не оттесняют их.
- Значения не теряются: 0/false/null/пустые наборы, длинные строки, массивы больше 10 элементов, сложные и широкие записи.
- Состояния ошибки, needs, отсутствия файлов и частичного результата проверены отдельными fixtures; исторический run дополняется подходящими тестовыми сценариями.
- Нет лишних сетевых или LLM-вызовов ради отображения, подмены исторических данных живой конфигурацией и новых предположений о достоверности результата.
- Привязка результатов к запуску, безопасные ссылки файлов и citations остаются корректными.
- Focused tests и type-check проходят; screenshots соответствуют последнему состоянию реализации.
